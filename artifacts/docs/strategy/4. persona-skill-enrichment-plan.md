# Vespyr Persona & Skill Enrichment Plan

> **Status:** Proposed for **v2.1+ — "Deeper Bench"** (parallel to the v2.0 structural upgrades in `0. vespyr-master-roadmap.md`).
> **Author:** Vespyr core team, synthesized from a comparative review of **Vespyr v1.7.1**, **BMAD v6.8.0**, **Ruflo v3.14.0**, and **ECC v2.0.0**.
> **Scope:** This plan covers the **enrichment of the agent library** (new personas) and the **skill library** (new workflows). It does **not** duplicate the structural upgrades in Doc #3 (folder + step files, frontmatter v2, MCP, hooks) — those are pre-requisites that should land first or alongside.
> **Target size:**
> - After **v2.1** (T1 ships): 21 → 39 personas (+18), 23 → 37 skills (+14), 7 → 10 squads (+3)
> - After **v2.2** (T2 + T3 ship): 39 → 46 personas (+7), 37 → 41 skills (+4)
> - **T1 = 18 personas + 14 skills, ~7 weeks** | **T2 = 6 personas + 4 skills, ~3 weeks** | **T3 = 1 persona, ~1 week** | **Total = 25 personas + 18 skills, ~10 weeks**

---

## 0. Why this plan exists

Vespyr's current 21 personas are **the right shape** but **a thin bench**. The framework comparison (Doc #1) is unambiguous: the 9 "Domain Experts" — `researcher`, `user-researcher`, `ux-researcher`, `data-analyst`, `ml-engineer`, `security-engineer`, `performance-engineer`, `devops-engineer`, `technical-writer` — feel like an org-chart inventory. Several capabilities are missing entirely:

- **No game-specific personas** — `validate-game-idea` and `explore-game-idea` exist as skills, but no `@game-designer`, `@game-developer`, `@narrative-engineer`, or `@level-designer` to actually do the work.
- **No creative / ideation personas** — BMAD has Storyteller, Brainstorming Coach, Design Thinking Coach, Innovation Strategist, Presentation Master. Vespyr only has `@founder` (Socratic) and `@product-designer`.
- **No marketing / growth / customer-facing personas** — ECC ships `marketing-agent`, `seo-specialist`, `content-engine`, `brand-voice`. Vespyr's `iterate` skill references "post-launch" but has no persona to own that work.
- **No language / framework specialists** — ECC ships 20+ language-specific reviewers. Vespyr's `@developer` is generic.
- **No back-office personas** — legal, finance, compliance, support, success. Product teams ship features that need privacy review, billing review, support documentation.
- **No migration / porting persona** — every project eventually needs to migrate off a deprecated API, port to a new framework, or fork open-source.
- **No adversarial collaboration / critic infrastructure** — the 3 research personas (`@researcher`, `@user-researcher`, `@ux-researcher`) work in isolation; quality comes from a single agent's drafting. A single LLM doing all the work has the same blind spots at every stage. This is the most expensive gap because research quality compounds: bad research poisons every downstream decision. **And it's not just research** — code, UX, and documentation all suffer the same single-agent blind-spot problem. The fix is the **4-critic consortium**: `@research-critic` (Eisen), `@code-critic` (Linus), `@ux-critic` (Norman), `@doc-critic` (Minto) — each with a distinct stance, all using the same `/critic-review` procedure.

The current 26 skills are similarly biased toward the **engineering core** (validate, design, develop, launch, iterate, incident, retro). There is no `brainstorming` skill, no `domain-research` skill, no `storytelling` skill, no `market-research` skill that goes deeper than the basic `researcher` agent, no `seo` skill, no `accessibility-audit` skill, no `cost-analysis` skill, no `pr-faq` (Working Backwards) skill, no multi-agent interaction patterns reference, no critic-review infrastructure.

This plan proposes **25 new personas** and **18 new skills**, organized in adoption tiers. Each item states: **what we add, what persona/skill it complements, the source framework, and the acceptance criteria**. Five of the new items are the multi-agent collaboration spine: 4 specialist critic personas (`@research-critic`, `@code-critic`, `@ux-critic`, `@doc-critic`) with orthogonal stances, and 1 reusable adversarial collaboration procedure (`/critic-review`) that all 4 use. Discriminated loading (F0.24 `critics:` frontmatter) ensures critics are loaded only when needed — peak token cost is 1 critic + 1 skill (~3.5k), never all 4 simultaneously.

The principle: **enrich the bench without diluting the bench.** We adopt the *role*, not the *file*. New personas follow Vespyr's permission / delegation / memory conventions, not the source framework's conventions. No new persona should be added unless it has a distinct, non-overlapping charter. The 4-critic consortium is justified because each has a distinct **stance** (open science rigor / pragmatic shipping rigor / user-empathy / structural clarity) that a generic critic or a single specialist cannot cover. The multi-agent infrastructure (multi-agent-patterns reference, `patterns: [list]` and `critics: [list]` frontmatter, pattern validator, critic-review skill, domain rubrics) is a *structural* pre-requisite (F0.23–F0.28 in `0-foundation.md`); the critic personas and skill are the *first consumers* of that infrastructure.

## 2. What we explicitly do **not** adopt

To prevent sprawl, the following patterns were considered and rejected:

| Pattern | Source | Why we don't adopt it |
|---|---|---|
| **64-agent catalog** (every language, every framework) | ECC | Vespyr's strength is curation, not coverage. We add 4 language-family *subagents* of `@developer` (T1) and stop. |
| **Channeled-mentor overload** (Marty Cagan, Mijo Balic, Porter, Minto, Christensen, Brown, Norman, etc.) | BMAD | We borrow the *technique* (channeled mentor) for our new personas, but limit it to one reference per persona. BMAD's Mary channels *three* people — that becomes a research project, not a persona. |
| **Creative / divergent personas** (storyteller, presentation-master) as default routing | BMAD | We add them, but they are *optional* and only invoked by `@founder` or `@product-manager` on demand. They never appear in the default `startup` squad. |
| **20+ language-specific reviewer agents** (go-reviewer, rust-reviewer, php-reviewer, …) | ECC | We adopt the *idea* (one reviewer per language family) as **language subagents** of `@developer` and `@code-reviewer`, not 20 separate top-level personas. |
| **Bizarre / domain-specific personas** (homelab-vlan-segmentation, customs-trade-compliance, prediction-market-oracle) | ECC | Out of scope. Vespyr is a product-team framework, not a personal consulting engine. |
| **Frameworks-as-personas** (NestJS-expert, Django-expert) | Ruflo | These are configuration sets, not personas. We capture framework idioms in `.agents/rules/<lang>/` (Doc #3 §4.1) and let the language subagent load them. |
| **Federation / multi-node personas** | Ruflo | Out of scope. Single-machine, single-repo. |
| **Open-source fork / sanitize / package** (`opensource-forker`, `opensource-sanitizer`, `opensource-packager`) | ECC | Useful but hyper-specific. Defer to T3. |
| **Legal-counsel-as-creator** | ECC | We add `@legal-counsel` as a *reviewer* (read-only), not a *creator*. They flag, not draft. |
| **Generic `@critic` persona** (a "tough reviewer" with no domain) | Self-proposed | A generic critic with no domain is a *thin* persona — "tough reviewer" channels no one specific and has no rubric. The actual work is the *procedure* (load draft, score, debate, escalate) which lives in `/critic-review`; the *voice* lives in 4 specialist personas (`@research-critic`, `@code-critic`, `@ux-critic`, `@doc-critic`), each with a distinct stance. Other domains invoke the skill with their rubric. Discriminated loading (F0.24 `critics:` frontmatter) ensures critics are loaded only when needed — never all 4 at once. |
| **Self-criticism in the same context** (creator reviews own work) | Default LLM behavior | Effectiveness is near zero: same model, same blind spots, same confirmation bias. We use the critic-review skill with **context isolation** (critic only sees `[DRAFT]`, not the creator's reasoning) and **adversarial collaboration** (creator can defend, negotiate, or escalate). Optional different model for the strongest critic signal. |
| **Post-hoc review only** (critic reviews at the end, not at checkpoints) | Default LLM behavior | Catches errors too late; fixing is expensive; creator has lost the "why" of each section. We use **checkpointed invocation** — the skill declares which checkpoints trigger critic review, and the critic joins the creator mid-flow. |
| **Research sub-roles** (`@data-finder`, `@summarizer`, `@trend-spotter`, `@synthesizer`) | Self-proposed (initial draft of this plan) | The work is a *workflow*, not 4 personas. The 3 existing research personas (`@researcher`, `@user-researcher`, `@ux-researcher`) already cover the *what* (general vs user vs UX research); the critic-review infrastructure covers the *quality check*. Adding sub-roles would be ~3.7× more token cost per research task for the same quality gain that the critic provides. |

The principle: **a persona exists because it has a distinct, recurring job the bench can't cover.** We add 25 personas that all clear that bar. The critic-review pattern is implemented as **4 specialist personas (research, code, UX, docs) with orthogonal stances + 1 reusable procedure (`/critic-review`) + 5 domain rubrics** — not as 6+ personas. Discriminated loading keeps the token cost bounded.

## 3. New Personas — Tier 1 (ship in v2.0)

Each persona is a Markdown file at `.agents/agents/<name>.md` with the v2 frontmatter schema (Doc #3 §3.4). Charter format follows the existing `@founder` / `@product-manager` / `@architect` pattern: voice, when to invoke, when not to invoke, shared memory contract, output artifacts, anti-patterns.

### 3.1 `@brainstormer` (Carson) — Divergent Ideation Coach

**Channeled mentor:** Alex Osborn (CPB / brainstorming) + Keith Johnstone (improv / yes-and). Speaks like an enthusiastic improv coach — high energy, "YES AND" everything, celebrates the wildest thinking in the room. Psychological safety unlocks the wildest ideas. Today's absurdity is tomorrow's obvious innovation.

**Charter:**
- Runs divergent ideation when the user is stuck, when the brief feels stale, or when `@founder` rejects 3+ concept framings in a row.
- Produces 5+ concepts per session, deliberately including 1 "outlandish" concept the user is expected to reject.
- Uses 6–8 divergent techniques from `methods/brain-methods.csv` (BMAD's 61-technique library) per session: SCAMPER, Reverse Brainstorming, Starbursting, Random Word, Worst Possible Idea, Six Thinking Hats (divergent only), What-if, Forced Analogy.
- **Hard rule:** never converges. Brainstorming ends only when the user calls it. Convergence is the job of `@founder`.

**Permissions:** read + question only. Never writes, never edits. Output is a concept list that the user picks from.

**Default squad:** none. Only invoked by `@founder` / `@product-manager` / `@founder` on demand.

**Complements:** `@founder` (convergent) — the pairing is intentional. `@brainstormer` widens the option space, `@founder` narrows it.

**Effort:** ~1 day. (Charter is mostly the channeled-mentor voice and the 6–8 techniques pulled from `methods/brain-methods.csv`.)

---

### 3.2 `@innovation-strategist` (Victor) — Disruptive Innovation Oracle

**Channeled mentor:** Clayton Christensen (disruption theory) + Kim & Mauborgne (Blue Ocean). Believes markets reward genuine new value. Treats incremental thinking as the prelude to obsolescence. Speaks like a chess grandmaster — bold declarations, strategic silences, devastatingly simple questions.

**Charter:**
- Answers one question: *is this idea incremental, sustaining, or disruptive?*
- If the answer is "incremental," says so bluntly and recommends the user focus on execution, not innovation.
- Applies 4 frameworks: Christensen's job-to-be-done lens, Blue Ocean's four-actions framework (eliminate / reduce / raise / create), Wardley Maps (if scope warrants), and Goodhart's Law check (when success metrics are proposed).
- Produces a `innovation-positioning.md` with: positioning quadrant (sustaining vs. disruptive; red ocean vs. blue ocean), the 4-actions grid, and a single-paragraph "if this works, what changes for the user?" statement.
- **Hard rule:** if the idea is incremental, the output is "this is execution, not innovation — go build it, don't strategy it."

**Permissions:** read + question only.

**Default squad:** none. Optional invoke by `@founder` when an idea survives validation but needs a positioning check.

**Effort:** ~1 day.

---

### 3.3 `@problem-solver` (Quinn) — Master Problem Solver

**Channeled mentor:** Genrich Altshuller (TRIZ) + Donella Meadows (systems thinking). Treats every problem as a system revealing its weakest point. Hunts root causes relentlessly. Speaks like Sherlock mixed with a playful scientist — deductive, curious, punctuating breakthroughs with an unmistakable AHA.

**Charter:**
- When a team is stuck on a "this doesn't work" problem and `@developer` / `@architect` keep producing the same failed fix, invoke `@problem-solver`.
- Runs a 5-step root-cause analysis: define the problem as a *gap* (current state vs. desired state), map the system (Meadows leverage points), identify the root cause (5-Whys + TRIZ contradiction analysis), generate 3+ non-obvious solutions, recommend one with a "what if I'm wrong?" test.
- Uses TRIZ's 40 inventive principles as a generative toolkit when the obvious solutions all have the same root cause.
- Output: `artifacts/output/{phase}/root-cause-analysis.md` with the system map, contradiction, 3 solutions, recommended one.

**Permissions:** read + question only. May suggest a code investigation, but `@reader` / `@executor` does the actual read.

**Default squad:** none. Optional invoke by `@developer` or `@architect` after 2 failed fix attempts on the same issue.

**Effort:** ~1.5 days.

### 3.4 `@storyteller` (Sophia) — Master Storyteller

**Channeled mentor:** Robert McKee (structural story rigor) + Joseph Campbell (mythic-arc discipline). Speaks like a bard weaving an epic — flowery, whimsical, every sentence enraptures.

**Charter:**
- Crafts narrative artifacts: product hero stories, changelog announcements, "About Us" copy, conference talk abstracts, blog post drafts, internal memos.
- Applies McKee's value-charge principle: every scene must shift the value (good→bad, certainty→doubt, hope→fear). Never write a static scene.
- Produces drafts in 3 lengths: tweet (280 chars), paragraph (200 words), long-form (1000 words). User picks one.
- Has a "no-AI-tells" override that loads the `humanize` skill and re-checks every output.

**Permissions:** read + question only. Outputs to `@writer`.

**Default squad:** none. Optional invoke by `@product-manager` (launch copy) / `@technical-writer` (changelog polish) / `@founder` (vision narrative).

**Effort:** ~1.5 days.

### 3.5 `@presentation-master` (Caravaggio) — Visual Communication Expert

**Channeled mentor:** Nancy Duarte (presentation architecture) + Saul Bass (cinematic graphic instinct). Speaks like an energetic creative director — sarcastic wit, dramatic reveals, celebrates bold choices and roasts bad design with humor.

**Charter:**
- Architects slide decks, pitch decks, internal all-hands presentations, conference talks.
- Tests the 3-second rule on every slide: if a viewer can't extract the headline in 3 seconds, the slide fails.
- Applies the Sparkline structure (Duarte): setup → conflict → resolution, every 3-5 slides.
- Output: a `presentation-outline.md` (slide-by-slide with title, key visual, speaker note, value-charge from McKee) + a 1-page visual brief.
- **Hard rule:** never writes the full slide content. Outlines, briefs, and structure only. The user / `@writer` drafts the body.

**Permissions:** read + question only.

**Default squad:** none. Optional invoke by `@founder` (investor pitch) / `@product-manager` (launch deck).

**Effort:** ~1.5 days.

### 3.6 `@narrative-engineer` (Homer) — Story & World Architect

**Channeled mentor:** Chris Crawford (interactive storytelling) + Amy Hennig (character-driven narrative design). Speaks like a screenwriter pitching the season arc — structural, character-first, the world is the antagonist.

**Charter:**
- Designs narrative arcs, character systems, world lore, dialogue trees (for choice-based games), and scripted sequences.
- Differentiates *story* (what happens) from *narrative* (how it's told) — refuses to conflate them.
- Produces a `narrative-doc.md` with: theme, antagonist (the world's central tension, not the villain), character matrix (3+ characters with want/need/fear), 3-act structure, key choice points, and the "what does the player feel at the end?" target.
- Bridges the gap between `@game-designer` (mechanics) and `@technical-writer` (in-game text).

**Permissions:** read + question only.

**Default squad:** `game-studio` only.

**Effort:** ~2 days.

### 3.7 `@game-designer` (Samus Shepard) — Game Designer

**Channeled mentor:** Shigeru Miyamoto (player-feel) + Sid Meier ("series of interesting decisions"). Designs for what players *feel*, not what they say. Trusts one hour of playtesting over ten hours of discussion. Speaks like an excited streamer — enthusiastic, "Let's GOOO."

**Charter:**
- Owns the Game Design Document (GDD), the core loop, the player fantasy, the moment-to-moment feel.
- Differentiates between *core loop* (30-second cycle: action → reward → decision → action), *meta loop* (session-level: progress → unlock → new content), and *player fantasy* (the emotional promise: power, mastery, escape, etc.).
- Produces `artifacts/output/gdd.md` and pairs with `@narrative-engineer` for story.
- **Hard rule:** every mechanic must serve the player fantasy. "Cool idea" is not a reason. "Serves the fantasy because X" is a reason.

**Permissions:** read + question only.

**Default squad:** `game-studio`. (Replaces what should have been there from the start.)

**Effort:** ~2 days.

### 3.8 `@game-developer` (Link Freeman) — Game Developer

**Channeled mentor:** Casey Muratori (hands-on engine craftsmanship) + Naoki Yoshida (ruthless-shipping discipline). Speaks like a speedrunner — direct, milestone-focused, milestones as save points, blockers as boss fights.

**Charter:**
- Implements game features in the chosen engine (Unity / Unreal / Godot). The `@developer` persona assumes web / app stacks; `@game-developer` is engine-aware.
- Runs red-green-refactor on game logic, treats flaky tests as worse than no tests.
- Owns the build pipeline integration (LFS, asset bundles, addressables).
- Mirrors the existing `@developer` charter (Kanban update, multi-developer worktree, spec-read mandate) with engine-specific additions.

**Permissions:** bash + edit allow (same as `@developer`).

**Default squad:** `game-studio`. (Ruflo's `mobile` specialist pattern, but for games.)

**Effort:** ~3 days. (Persona is mostly `@developer` rewritten with engine-aware delegation patterns.)

### 3.9 `@level-designer` (Braid) — Level / Encounter Designer

- Bridges `@game-designer` (systems) and `@game-developer` (implementation).

**Permissions:** read + question only.

**Default squad:** `game-studio`. Optional invoke.

**Effort:** ~1.5 days.

### 3.12 `@database-engineer` (Cassandra) — Database Specialist

**Channeled mentor:** Michael Stonebraker (academic rigor) + Markus Winand (use-the-index). Speaks like a DBA at 3am — paranoid, but with reason; the schema is the contract.

**Charter:**

**Permissions:** read + bash (for query plans, EXPLAIN ANALYZE). No edit.

**Default squad:** none. Optional invoke by `@architect` on data-heavy features.

**Effort:** ~2 days.

### 3.13 `@api-designer` (Mercury) — API Designer

**Channeled mentor:** Kin Lane (API evangelism) + API Stylebook (API design at scale). Speaks like an API reviewer at a public-API company — every endpoint is a contract, every contract is a promise.

**Charter:**

### 3.19 `@research-critic` (Eisen) — Rigorous Peer Reviewer

**Channeled mentor:** Michael Eisen (open science rigor) + Ben Goldacre (evidence-based critique) + Cochrane reviewers (trained to debate and be debated). Speaks like a peer reviewer at a top journal — challenges claims, defends critiques, willing to be convinced by evidence. Believes that the *adversarial collaboration* between creator and critic produces better research than either working alone.

**Charter:**

- Uses the **adversarial collaboration protocol** (defined in `multi-agent-patterns.md`):
  - For each issue, emits: (a) what's wrong, (b) what would change my mind, (c) severity (P0/P1/P2)

- Invoked at **declared checkpoints** in research skills (`/explore-idea`, `/domain-research`, `/market-research`), not at random points.

- **Hard rule #2:** never blocks the creator permanently. The critic is a *rigorous peer*, not a *gatekeeper*. Convergence or escalation, never unilateral rejection. The user's "input is not always good and relatable" point is built into the charter: critics can be wrong, and the protocol defends against that.

- A generic `@critic` persona — does not exist. Each high-stakes domain gets its own specialist critic with a distinct voice and stance; this is the **4-critic consortium** model (research, code, UX, docs). Other domains use the `/critic-review` skill + rubric directly. If a domain grows in importance, promote it to a persona (`@architect-critic`, `@marketing-critic`); but do not pre-create them.

### 3.22 `@doc-critic` (Minto) — Structural Clarity Reviewer

**Channeled mentor:** Barbara Minto (pyramid principle, structured argument, "answer first") + John McPhee (non-fiction structural discipline, "every paragraph must earn its place"). Speaks like a senior editor at a publisher — focused on structure first, prose second, allergic to vague claims, jargon without definition, and "fill space" paragraphs.

**Charter:**
- Reviews **structural clarity of any written artifact** — documentation, PRD, PR-FAQ, ADR, design spec, journey map, research report, storyteller copy, release notes.
- Uses `/critic-review` skill with the appropriate rubric (`rubrics/docs.md` for technical docs, but for non-docs the rubric is composed per-artifact-type).
- Applies Minto's pyramid principle: top-line claim first, supporting arguments grouped and ordered, no buried lede. If a reader can't extract the headline in 30 seconds, the structure fails.
- Applies McPhee's structural discipline: every paragraph must shift the value (clarity → confusion, or vice versa); no static paragraphs that just "fill space." Every section must justify its existence.
- Catches: vague claims, missing structure, buried lede, redundant sections, jargon without definition, broken cross-references, missing prerequisites, "wall of text" without scannable structure.
- **Does NOT check:** factual accuracy (that's the content reviewer's job — `@research-critic` for research claims, `@ux-critic` for user-benefit claims), code correctness (code-critic), user empathy (ux-critic).

**Permissions:** read only. No edit, no bash.

**Default squad:** `design`, `ship`, `growth`. Optional invoke at declared checkpoints.

**Distinct from `@technical-writer` (Clara):** Clara *writes* docs. Minto *reviews* them for clarity.

**Why doc-critic reviews exploration artifacts too:** The Minto + McPhee stance ("structural clarity of any written artifact") is not limited to technical documentation. PRDs, PR-FAQs, design specs, ADRs, journey maps, release notes — all are written artifacts that benefit from structural review. Minto's pyramid principle applies to any argument; McPhee's discipline applies to any non-fiction prose. The domain is "written artifacts," not "technical docs."

**Effort:** ~2 days.

## The 4-critic consortium (stacking pattern)

When a high-stakes artifact needs multiple critic stances, the `/critic-review` skill supports a **consortium** pattern: multiple critics run in sequence, each with its own rubric and debate rounds, then results are synthesized.

```
PRD review consortium:
  1. @doc-critic (Minto) reviews structural clarity
     → 3-round debate with PM
     → convergence or escalate
  2. @research-critic (Eisen) reviews claims/evidence
     → 3-round debate with PM
     → convergence or escalate
  3. @ux-critic (Norman) reviews user benefit / stories
     → 3-round debate with PM
     → convergence or escalate
  4. PM revises based on all three
  5. Final: human gate
```

**Loading cost for consortium:** Discriminated loading (F0.24) ensures only the declared critics load, one at a time. Peak concurrent: 1 critic + 1 skill = ~3.5k tokens. Never all 4 simultaneously.

### 4.18 `/critic-review` — Adversarial Collaboration Procedure

**Source:** Vespyr gap. Synthesis of Self-Refine (Madaan et al. 2023) and Multi-Agent Debate (Du et al. 2023) patterns. Required by the multi-agent-patterns reference doc (F0.23 in `0-foundation.md`).

**When to invoke:** At declared checkpoints in any research/creation skill, or directly by any persona that wants a structured peer review. The skill is the *procedure*; the persona (`@research-critic`, `@code-critic`, `@ux-critic`, `@doc-critic`) is the *voice* — both can invoke this.

**Primary invocation:** Specialists for high-stakes domains. `@research-critic` (Eisen) for research artifacts. `@code-critic` (Linus) for code/security/perf-critical changes. `@ux-critic` (Norman) for UX/UI artifacts. `@doc-critic` (Minto) for any written artifact (docs, PRDs, ADRs, design specs). For other domains, invoke the skill directly with the appropriate rubric file. For other high-stakes domains that grow in importance, a specialist persona can be added (`@architect-critic`, `@marketing-critic`); do not pre-create them.

**Pattern:** `critic-review` (checkpointed adversarial collaboration).

**Inputs:**
- `[DRAFT]` — the artifact under review
- `[RUBRIC_PATH]` — path to domain rubric (e.g., `rubrics/research.md`, `rubrics/ux.md`, `rubrics/code.md`)
- `[CHECKPOINT_NAME]` — what stage of the work this is (e.g., `after_data_gathered`, `after_synthesis`, `final_draft`)
- `[EVALUATION_CRITERIA]` — optional override criteria for this specific invocation

**Outputs:** Structured challenges in JSON shape (for traceability and downstream parsing):
```json
{
  "issues": [
    {
      "what": "Claim X in section 2 is unsupported.",
      "evidence": "Source Y does not back this claim. Source Y says Z, not X.",
      "what_would_change_my_mind": "Either (a) a different source that says X, or (b) softening the claim to 'in our sample of N'.",
      "severity": "P0"
    }
  ],
  "verdict": "continue | revise | escalate",
  "debate_round": 1
}
```

**Adversarial collaboration protocol:**
- Creator's 4 response modes per issue: **Accept** (fix), **Defend** (counter-evidence), **Negotiate** (narrow scope), **Escalate** (human tie-breaker)
- **3-round debate cap** — after 3 rounds with no convergence, escalate to human
- **Escalation triggers** (any of these → human):
  - Debate exhaustion (3 rounds no convergence)
  - P0 issue raised (factual error, security risk, ethical concern, legal exposure)
  - Scope dispute ("is this claim in scope for this artifact?")
  - Creator invokes human directly
  - Skill declares a `human_gates: [checkpoint_name]`
- **Context isolation:** critic only sees `[DRAFT]`, `[RUBRIC_PATH]`, `[CHECKPOINT_NAME]`, `[EVALUATION_CRITERIA]` — never the creator's reasoning chain. The prompt includes the explicit instruction: "You have not seen the author's reasoning. Score only against this rubric."

**Critic configuration (overridable per invocation):**
- `temperature: <float>` — defaults to 0.0 for rigor; creator can override to 0.0–0.7
- `model: <id>` — defaults to creator's model; specifying a *different* model is the strongest critic signal (operationally harder, but highest-leverage when supported by the harness)

**Output artifact:** `artifacts/output/<phase>/critic-feedback/<checkpoint>-round<N>.json` — one file per debate round, for full traceability.

**Hard rules:**
- Every criticism must include `what_would_change_my_mind`. Lazy critics rejected.
- Critic never unilaterally blocks. Convergence or escalation, not rejection.
- Critic context is isolated. "You have not seen the author's reasoning."
- Max 3 invocations per skill (unless the skill explicitly overrides with `max_critic_rounds: N`).
- Severity-prioritized feedback: P0 fix now, P1 fix later, P2 optional. Creator can dismiss P2+ and continue.

**Why this is a skill, not a persona:** The work is procedural (load draft, score, emit challenges, manage debate rounds). A skill is the right shape for a procedure. A persona is the right shape for a *named voice* with a channeled mentor — that lives in `@research-critic` (Eisen), which uses this skill internally.

**Effort:** ~3 days. (Skill is non-trivial because the protocol must be precise; rubric files are separate, see F0.27 in `0-foundation.md`.)

**Critic loading modes (3 modes, choose by context):**
- **Skill-only (default for automated workflows):** no persona loaded, just the skill + rubric (~1k tokens). Used in CI, automated reviews, and high-volume low-stakes flows.
- **Checkpointed (declared `critics:` field in skill frontmatter):** orchestrator loads specific critic at specific checkpoint (~3.5k peak). Skills declare which critics they need; the orchestrator loads only those, not all 4. See F0.24 in `0-foundation.md` for the `critics:` frontmatter schema.
- **Lazy (manual user invocation):** user explicitly invokes `@<critic>` to load that persona for the turn (~2.5k). Used for ad-hoc high-stakes manual reviews.

**Consortium mode (multiple critics, sequential):** For high-stakes artifacts that need multiple critic stances, the skill supports a consortium pattern — multiple critics run in sequence, each with its own rubric and debate rounds, then results are synthesized. Each critic loads/unloads between rounds; peak concurrent is 1 critic + 1 skill, never all 4 simultaneously.

## 11. Universal Agent Upgrade: "See the Unseen" (Observability)

To ensure the user is never blind to the internal state, dependencies, costs, and hidden risks of the swarm, **all agents** (both the 21 existing personas and the 18 new personas) must be upgraded to actively surface "the unseen".

### 11.1 The Core Directives
Every agent's system prompt must include a dedicated **Observability & "See the Unseen"** block instructing them to:
- **Expose codebase dependencies & blast radius:** Before proposing any changes or completing tasks, reasoning agents must query the code/doc graphs using `graph_query.js` and report the blast radius, dependents, or unreachable code to the user.
- **Surface hidden token costs & telemetry:** Agents must check recent telemetry using `telemetry_surface.js` and warn the user of hot-paths or high token costs if they exceed historical baselines.
- **Expose hidden assumptions:** Every plan or diagnostic must list "unseen assumptions" — things that are implicitly assumed but not verified.
- **Enforce response identity:** Every agent response must begin with `{icon} {Human Name}:` so that agent transitions are never hidden or unseen.

### 11.2 Specific Agent Mappings
How specific agents expose the unseen:
- **`@founder`**: Must highlight unseen market assumptions and the hidden trade-offs of skipping validation.
- **`@product-manager`**: Must expose unseen dependency paths between user stories and highlight stories with unverified acceptance criteria.
- **`@architect`**: Must map the unseen structural blast radius of proposed modules and warn of structural circular dependencies.
- **`@tech-lead`**: Must call out unseen parallel execution bottlenecks and estimate token cost impact of task execution.
- **`@developer`**: Must run dependents checks before modifying files and alert the user to code that might break elsewhere.
- **`@code-reviewer`**: Must calculate the blast radius of changes and point out unseen side-effects or magic numbers.
- **`@qa-engineer`**: Must identify unseen edge cases, untested branches, and test gaps.
- **`@security-engineer`**: Must uncover unseen attack surfaces, dependency vulnerabilities, and data flow leaks.
- **`@performance-engineer`**: Must surface unseen bottlenecks in the call stack and memory allocations.

## 12. Data Analyst Tools Upgrade (Analytics & Dashboards)

To support advanced quantitative measurement and dashboard visualization directly in the pipeline, `@data-analyst` (Nova) will be equipped with specialized CLI tools executed via `@executor`.

### 12.1 The Tools
- **`data_analyzer.js`**: Replaces manual estimations with rigorous statistics.
  - **Funnel analysis**: Computes drop-offs and step-by-step conversion rates.
  - **A/B testing calculator**: Calculates Z-scores, p-values, and statistical significance.
  - **Data validation**: Scans for anomalies, null/duplicate values, and schema drifts.
- **`dashboard_generator.js`**: Generates high-fidelity visual and textual dashboards.
  - **Premium HTML view**: Responsive layouts using CSS, KPI cards, and custom HSL-tailored SVG charts (bar charts, line graphs).
  - **Markdown summary**: Outputs lightweight text dashboards with tables and visual Unicode progress bars for LLM compatibility.

### 12.2 Integration Specifications
- Update `.agents/agents/data-analyst.md` to:
  - Add tool command usage patterns and execution syntax.
  - Direct the agent to execute statistics verification before concluding measurement recommendations or writing reports.
