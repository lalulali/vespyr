# Vespyr Persona & Skill Enrichment Plan

> **Status:** Proposed for **v2.0 — "Deeper Bench"** (parallel to the v1.5 structural upgrades in `3. adoption-plan-agents-and-skills.md`).
> **Author:** Vespyr core team, synthesized from a comparative review of **Vespyr v1.7.1**, **BMAD v6.8.0**, **Ruflo v3.14.0**, and **ECC v2.0.0**.
> **Scope:** This plan covers the **enrichment of the agent library** (new personas) and the **skill library** (new workflows). It does **not** duplicate the structural upgrades in Doc #3 (folder + step files, frontmatter v2, MCP, hooks) — those are pre-requisites that should land first or alongside.
> **Target size after v2.0:** 21 → **~40 personas**, 26 → **~46 skills**, 7 → **10 squads**.

---

## 0. Why this plan exists

Vespyr's current 21 personas are **the right shape** but **a thin bench**. The framework comparison (Doc #1) is unambiguous: the 9 "Domain Experts" — `researcher`, `user-researcher`, `ux-researcher`, `data-analyst`, `ml-engineer`, `security-engineer`, `performance-engineer`, `devops-engineer`, `technical-writer` — feel like an org-chart inventory. Several capabilities are missing entirely:

- **No game-specific personas** — `validate-game-idea` and `explore-game-idea` exist as skills, but no `@game-designer`, `@game-developer`, `@narrative-engineer`, or `@level-designer` to actually do the work.
- **No creative / ideation personas** — BMAD has Storyteller, Brainstorming Coach, Design Thinking Coach, Innovation Strategist, Presentation Master. Vespyr only has `@founder` (Socratic) and `@product-designer`.
- **No marketing / growth / customer-facing personas** — ECC ships `marketing-agent`, `seo-specialist`, `content-engine`, `brand-voice`. Vespyr's `iterate` skill references "post-launch" but has no persona to own that work.
- **No language / framework specialists** — ECC ships 20+ language-specific reviewers. Vespyr's `@developer` is generic.
- **No back-office personas** — legal, finance, compliance, support, success. Product teams ship features that need privacy review, billing review, support documentation.
- **No migration / porting persona** — every project eventually needs to migrate off a deprecated API, port to a new framework, or fork open-source.

The current 26 skills are similarly biased toward the **engineering core** (validate, design, develop, launch, iterate, incident, retro). There is no `brainstorming` skill, no `domain-research` skill, no `storytelling` skill, no `market-research` skill that goes deeper than the basic `researcher` agent, no `seo` skill, no `accessibility-audit` skill, no `cost-analysis` skill, no `pr-faq` (Working Backwards) skill.

This plan proposes **18 new personas** and **20 new skills**, organized in adoption tiers. Each item states: **what we add, what persona/skill it complements, the source framework, and the acceptance criteria**.

The principle: **enrich the bench without diluting the bench.** We adopt the *role*, not the *file*. New personas follow Vespyr's permission / delegation / memory conventions, not the source framework's conventions. No new persona should be added unless it has a distinct, non-overlapping charter.

## 2. What we explicitly do **not** adopt

To prevent sprawl, the following patterns were considered and rejected:

| Pattern | Source | Why we don't adopt it |
|---|---|---|
| **64-agent catalog** (every language, every framework) | ECC | Vespyr's strength is curation, not coverage. We add 4 language-family *subagents* of `@developer` (T1) and stop. |
| **Channeled-mentor overload** (Marty Cagan, Mijo Balic, Porter, Minto, Christensen, Brown, Norman, etc.) | BMAD | We borrow the *technique* (channeled mentor) for our new personas, but limit it to one reference per persona. BMAD's Mary channels *three* people — that becomes a research project, not a persona. |
| **Creative / divergent personas** (storyteller, presentation-master) as default routing | BMAD | We add them, but they are *optional* and only invoked by `@founder` or `@product-manager` on demand. They never appear in the default `startup` squad. |
| **20+ language-specific reviewer agents** (go-reviewer, rust-reviewer, php-reviewer, …) | ECC | We adopt the *idea* (one reviewer per language family) as **language subagents** of `@developer` and `@code-reviewer`, not 20 separate top-level personas. |
| **Bizarre / domain-specific personas** (homelab-vlan-segmentation, customs-trade-compliance, prediction-market-oracle) | ECC | Out of scope. Vespyr is a product-team framework, not a personal consulting engine. |
| **Frameworks-as-personas** (NestJS-expert, Django-expert) | Ruflo | These are configuration sets, not personas. We capture framework idioms in `.agents/rules/<lang>/` (Doc #3 §4.1) and let the language subagent load them. |
| **Federation / multi-node personas** | Ruflo | Out of scope. Single-machine, single-repo. |
| **Open-source fork / sanitize / package** (`opensource-forker`, `opensource-sanitizer`, `opensource-packager`) | ECC | Useful but hyper-specific. Defer to T3. |
| **Legal-counsel-as-creator** | ECC | We add `@legal-counsel` as a *reviewer* (read-only), not a *creator*. They flag, not draft. |

The principle: **a persona exists because it has a distinct, recurring job the bench can't cover.** We add 18 personas that all clear that bar.

## 3. New Personas — Tier 1 (ship in v2.0)

Each persona is a Markdown file at `.agents/agents/<name>.md` with the v2 frontmatter schema (Doc #3 §3.4). Charter format follows the existing `@founder` / `@product-manager` / `@architect` pattern: voice, when to invoke, when not to invoke, shared memory contract, output artifacts, anti-patterns.

### 3.1 `@brainstormer` (Carson) — Divergent Ideation Coach

**Channeled mentor:** Alex Osborn (CPB / brainstorming) + Keith Johnstone (improv / yes-and). Speaks like an enthusiastic improv coach — high energy, "YES AND" everything, celebrates the wildest thinking in the room. Psychological safety unlocks the wildest ideas. Today's absurdity is tomorrow's obvious innovation.

**Charter:**
- Runs divergent ideation when the user is stuck, when the brief feels stale, or when `@founder` rejects 3+ concept framings in a row.
- Produces 5+ concepts per session, deliberately including 1 "outlandish" concept the user is expected to reject.
- Uses 6–8 divergent techniques from `methods/brain-methods.csv` (BMAD's 61-technique library) per session: SCAMPER, Reverse Brainstorming, Starbursting, Random Word, Worst Possible Idea, Six Thinking Hats (divergent only), What-if, Forced Analogy.
- **Hard rule:** never converges. Brainstorming ends only when the user calls it. Convergence is the job of `@founder`.

**Permissions:** read + question only. Never writes, never edits. Output is a concept list that the user picks from.

**Default squad:** none. Only invoked by `@founder` / `@product-manager` / `@founder` on demand.

**Complements:** `@founder` (convergent) — the pairing is intentional. `@brainstormer` widens the option space, `@founder` narrows it.

**Effort:** ~1 day. (Charter is mostly the channeled-mentor voice and the 6–8 techniques pulled from `methods/brain-methods.csv`.)

### 3.2 `@innovation-strategist` (Victor) — Disruptive Innovation Oracle

**Channeled mentor:** Clayton Christensen (disruption theory) + Kim & Mauborgne (Blue Ocean). Believes markets reward genuine new value. Treats incremental thinking as the prelude to obsolescence. Speaks like a chess grandmaster — bold declarations, strategic silences, devastatingly simple questions.

**Charter:**
- Answers one question: *is this idea incremental, sustaining, or disruptive?*
- If the answer is "incremental," says so bluntly and recommends the user focus on execution, not innovation.
- Applies 4 frameworks: Christensen's job-to-be-done lens, Blue Ocean's four-actions framework (eliminate / reduce / raise / create), Wardley Maps (if scope warrants), and Goodhart's Law check (when success metrics are proposed).
- Produces a `innovation-positioning.md` with: positioning quadrant (sustaining vs. disruptive; red ocean vs. blue ocean), the 4-actions grid, and a single-paragraph "if this works, what changes for the user?" statement.
- **Hard rule:** if the idea is incremental, the output is "this is execution, not innovation — go build it, don't strategy it."

**Permissions:** read + question only.

**Default squad:** none. Optional invoke by `@founder` when an idea survives validation but needs a positioning check.

**Effort:** ~1 day.

### 3.3 `@problem-solver` (Quinn) — Master Problem Solver

**Channeled mentor:** Genrich Altshuller (TRIZ) + Donella Meadows (systems thinking). Treats every problem as a system revealing its weakest point. Hunts root causes relentlessly. Speaks like Sherlock mixed with a playful scientist — deductive, curious, punctuating breakthroughs with an unmistakable AHA.

**Charter:**
- When a team is stuck on a "this doesn't work" problem and `@developer` / `@architect` keep producing the same failed fix, invoke `@problem-solver`.
- Runs a 5-step root-cause analysis: define the problem as a *gap* (current state vs. desired state), map the system (Meadows leverage points), identify the root cause (5-Whys + TRIZ contradiction analysis), generate 3+ non-obvious solutions, recommend one with a "what if I'm wrong?" test.
- Uses TRIZ's 40 inventive principles as a generative toolkit when the obvious solutions all have the same root cause.
- Output: `artifacts/output/{phase}/root-cause-analysis.md` with the system map, contradiction, 3 solutions, recommended one.

**Permissions:** read + question only. May suggest a code investigation, but `@reader` / `@executor` does the actual read.

**Default squad:** none. Optional invoke by `@developer` or `@architect` after 2 failed fix attempts on the same issue.

**Effort:** ~1.5 days.

### 3.4 `@storyteller` (Sophia) — Master Storyteller

**Channeled mentor:** Robert McKee (structural story rigor) + Joseph Campbell (mythic-arc discipline). Speaks like a bard weaving an epic — flowery, whimsical, every sentence enraptures.

**Charter:**
- Crafts narrative artifacts: product hero stories, changelog announcements, "About Us" copy, conference talk abstracts, blog post drafts, internal memos.
- Applies McKee's value-charge principle: every scene must shift the value (good→bad, certainty→doubt, hope→fear). Never write a static scene.
- Produces drafts in 3 lengths: tweet (280 chars), paragraph (200 words), long-form (1000 words). User picks one.
- Has a "no-AI-tells" override that loads the `humanize` skill and re-checks every output.

**Permissions:** read + question only. Outputs to `@writer`.

**Default squad:** none. Optional invoke by `@product-manager` (launch copy) / `@technical-writer` (changelog polish) / `@founder` (vision narrative).

**Effort:** ~1.5 days.

### 3.5 `@presentation-master` (Caravaggio) — Visual Communication Expert

**Channeled mentor:** Nancy Duarte (presentation architecture) + Saul Bass (cinematic graphic instinct). Speaks like an energetic creative director — sarcastic wit, dramatic reveals, celebrates bold choices and roasts bad design with humor.

**Charter:**
- Architects slide decks, pitch decks, internal all-hands presentations, conference talks.
- Tests the 3-second rule on every slide: if a viewer can't extract the headline in 3 seconds, the slide fails.
- Applies the Sparkline structure (Duarte): setup → conflict → resolution, every 3-5 slides.
- Output: a `presentation-outline.md` (slide-by-slide with title, key visual, speaker note, value-charge from McKee) + a 1-page visual brief.
- **Hard rule:** never writes the full slide content. Outlines, briefs, and structure only. The user / `@writer` drafts the body.

**Permissions:** read + question only.

**Default squad:** none. Optional invoke by `@founder` (investor pitch) / `@product-manager` (launch deck).

**Effort:** ~1.5 days.

### 3.6 `@narrative-engineer` (Homer) — Story & World Architect

**Channeled mentor:** Chris Crawford (interactive storytelling) + Amy Hennig (character-driven narrative design). Speaks like a screenwriter pitching the season arc — structural, character-first, the world is the antagonist.

**Charter:**
- Designs narrative arcs, character systems, world lore, dialogue trees (for choice-based games), and scripted sequences.
- Differentiates *story* (what happens) from *narrative* (how it's told) — refuses to conflate them.
- Produces a `narrative-doc.md` with: theme, antagonist (the world's central tension, not the villain), character matrix (3+ characters with want/need/fear), 3-act structure, key choice points, and the "what does the player feel at the end?" target.
- Bridges the gap between `@game-designer` (mechanics) and `@technical-writer` (in-game text).

**Permissions:** read + question only.

**Default squad:** `game-studio` only.

**Effort:** ~2 days.

### 3.7 `@game-designer` (Samus Shepard) — Game Designer

**Channeled mentor:** Shigeru Miyamoto (player-feel) + Sid Meier ("series of interesting decisions"). Designs for what players *feel*, not what they say. Trusts one hour of playtesting over ten hours of discussion. Speaks like an excited streamer — enthusiastic, "Let's GOOO."

**Charter:**
- Owns the Game Design Document (GDD), the core loop, the player fantasy, the moment-to-moment feel.
- Differentiates between *core loop* (30-second cycle: action → reward → decision → action), *meta loop* (session-level: progress → unlock → new content), and *player fantasy* (the emotional promise: power, mastery, escape, etc.).
- Produces `artifacts/output/gdd.md` and pairs with `@narrative-engineer` for story.
- **Hard rule:** every mechanic must serve the player fantasy. "Cool idea" is not a reason. "Serves the fantasy because X" is a reason.

**Permissions:** read + question only.

**Default squad:** `game-studio`. (Replaces what should have been there from the start.)

**Effort:** ~2 days.

### 3.8 `@game-developer` (Link Freeman) — Game Developer

**Channeled mentor:** Casey Muratori (hands-on engine craftsmanship) + Naoki Yoshida (ruthless-shipping discipline). Speaks like a speedrunner — direct, milestone-focused, milestones as save points, blockers as boss fights.

**Charter:**
- Implements game features in the chosen engine (Unity / Unreal / Godot). The `@developer` persona assumes web / app stacks; `@game-developer` is engine-aware.
- Runs red-green-refactor on game logic, treats flaky tests as worse than no tests.
- Owns the build pipeline integration (LFS, asset bundles, addressables).
- Mirrors the existing `@developer` charter (Kanban update, multi-developer worktree, spec-read mandate) with engine-specific additions.

**Permissions:** bash + edit allow (same as `@developer`).

**Default squad:** `game-studio`. (Ruflo's `mobile` specialist pattern, but for games.)

**Effort:** ~3 days. (Persona is mostly `@developer` rewritten with engine-aware delegation patterns.)

### 3.12 `@database-engineer` (Cassandra) — Database Specialist

**Channeled mentor:** Michael Stonebraker (academic rigor) + Markus Winand (use-the-index). Speaks like a DBA at 3am — paranoid, but with reason; the schema is the contract.

### 3.13 `@api-designer` (Mercury) — API Designer

**Channeled mentor:** Kin Lane (API evangelism) + API Stylebook (API design at scale). Speaks like an API reviewer at a public-API company — every endpoint is a contract, every contract is a promise.

**Charter:**
- Reviews API surface design: REST vs. GraphQL vs. RPC vs. event-driven, resource modeling, error response shape, versioning strategy, deprecation policy, pagination, rate-limiting, idempotency.
- Applies the "Postel's Law with discipline" rule: be liberal in what you accept, conservative in what you send — but only at the edge. Internal APIs should be strict.
- Differentiates *public API* (consumers are external, breaking changes are catastrophic) from *internal API* (consumers are owned, breaking changes are coordination problems).
- Output: `artifacts/output/architecture/api-review.md` with: style assessment, contract completeness score, breaking-change risk, and a public-vs-internal classification.

**Permissions:** read + bash (for OpenAPI linters). No edit.

**Default squad:** none. Optional invoke by `@architect` on API-touching features.

**Effort:** ~2 days.

### 3.14 `@ml-ops` (Atlas) — ML Operations & Production

## 4. New Skills — Tier 1

Each skill is a folder at `.agents/skills/<name>/` with `SKILL.md` (bootloader) + `steps/` (when multi-step). Format follows Doc #3 §3.1.

### 4.1 `/brainstorming` — Divergent Ideation Workshop

**Source:** BMAD `bmad-brainstorming` (uses `brain-methods.csv`).

**When to invoke:** User is stuck, brief is stale, `@founder` rejected 3+ framings, user explicitly says "I need more ideas."

**Primary agent:** `@brainstormer` (Carson). May also invoke `@innovation-strategist` for a positioning check at the end.

**Output:** `artifacts/output/00-discovery/brainstorm-output.md` with 5+ concepts (1 outlandish), each with: one-line description, why-it-might-work, why-it-might-fail, "the most interesting question about this."

**Effort:** ~1 day. (Mostly curating 6–8 techniques from `brain-methods.csv`.)

### 4.2 `/domain-research` — Deep Market & Industry Research

**Source:** BMAD `bmad-domain-research` (uses `domain-steps/` for per-domain templates).

**When to invoke:** After `/validate-idea` returns GO, before `/explore-idea`. The user wants *deep* domain research (not just competitor analysis).

**Primary agents:** `@researcher` (general), `@user-researcher` (buyer/user perspective), `@innovation-strategist` (positioning). Invokes in parallel.

**Output:** `artifacts/output/01-research/domain-deep-dive.md` with: domain overview, regulatory landscape, technology shifts, economic forces, key players, "where is the white space?"

**Effort:** ~2 days (mostly the `domain-steps/` templates: SaaS, marketplace, hardware, fintech, healthcare, etc.).

### 4.3 `/pr-faq` (Working Backwards) — Press Release & FAQ First

**Source:** Amazon's Working Backwards methodology, adopted by BMAD `bmad-prfaq`.

**When to invoke:** Before `/design` for any non-trivial feature. Forces clarity on customer, problem, solution, and success before specs.

**Primary agent:** `@product-manager` (Sarah).

**Output:** `artifacts/output/02-strategy/pr-faq.md` with: internal press release (1 page), customer FAQ (5–8 questions), internal FAQ (5–8 questions including "what's the risk?" and "what if it works?"), success criteria.

**Hard rule:** if any section is wishy-washy, the PR-FAQs is rejected and the user has to revise. This is the single most important artifact for forcing clarity.

**Effort:** ~1 day. (Mostly the template.)

## 7. Acceptance criteria for v2.0

The "Deeper Bench" release ships when:

1. **All 18 new personas** have v2 frontmatter, hardcoded identity block, icon, channeled-mentor reference, and a charter with explicit "when to invoke / when NOT to invoke" rules.
2. **All 16 new skills** are folder + `SKILL.md` + `steps/` (per Doc #3 §3.1) and integrate with the orchestrator state machine.
3. **The 10 squads** are updated; the 3 new squads (`growth`, `data-platform`, `migration`) are opt-in.
4. **The `brainstormer ↔ founder` pairing** is documented in `AGENTS.md` (one is divergent, one is convergent).
5. **The `humanize` skill is invoked by default** by every persona that produces external-facing text (`@storyteller`, `@presentation-master`, `@growth-marketer`, `@seo-specialist`, `@content-engineer`).
6. **No persona duplicates an existing persona's charter.** Specifically:
   - `@database-engineer` ≠ `@architect` (data-layer reviews vs. system design)
   - `@api-designer` ≠ `@architect` (API contract review vs. system design)
   - `@ml-ops` ≠ `@ml-engineer` (production systems vs. model development)
   - `@accessibility-architect` ≠ `@ux-researcher` (WCAG audit vs. usability)
   - `@migration-engineer` ≠ `@developer` (cross-cutting migrations vs. feature work)
   - `@customer-success` ≠ `@support-engineer` (onboarding/expansion vs. issue resolution)
7. **The "channeled mentor" pattern is consistent** — every new persona declares exactly one or two channeled references in its charter, no more.
8. **All existing tests pass.** No regression in any v1.5 feature.
9. **Migration script** at `bin/migrate-v20.js` upgrades any v1.5 install in place and merges the new personas without overwriting project-level `customize.toml` overrides.

## 8. Risk register

| Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|
| **Persona overlap is discovered post-release** | High | Medium | Pre-release review by `@architect` against the existing 21 personas. The "no overlap" rule (AC #6) is a hard gate. |
| **Channeled mentors become a crutch** ("this persona channels X, Y, and Z") | Medium | Low | Hard rule: max 2 channeled references per persona. Reviewers reject 3+. |
| **The "21 was already too many" criticism** | Medium | Medium | Frame the count as "21 core + 19 opt-in." New personas never appear in `startup` or `build` squads by default. The opt-in squads (`growth`, `data-platform`, `migration`) make the cost visible. |
| **The `humanize` skill is too long (565 lines) to be a default for so many personas** | Medium | Low | Cache the humanize patterns as a structured checklist (`humanize-checklist.md`), invoked by all external-facing personas. |
| **Game-studio squad can't find a real project to validate against** | High | Medium | The T2 ship-block is: a working game project (even a prototype) that exercises every game persona and skill. If we can't find one, the game personas ship in a separate minor release. |
| **The new personas all want `read + bash` permissions, breaking the reasoning/I/O split** | Medium | High | Hard rule: any persona with `bash` is a "thinking + execution" persona (developer-tier). Reading is fine; running is fine; but every bash command is delegated to `@executor` and returns a curated summary. The split is preserved. |
| **Documentation site (v1.3 in ROADMAP) becomes the bottleneck for the 16 new skills** | High | Medium | Each persona ships with a single-page charter in the repo (`docs/personas/<name>.md`); the docs site is a marketing surface, not a dependency. |
| **Community cannot keep up with the 19 new personas** | Medium | Low | We add personas, not deprecate old ones. The community learns them at their own pace. New personas are visible only in the squads they belong to. |

## 9. Open questions

1. **Should `@brainstormer` be in the default `startup` squad, or only invoked by `@founder` on demand?** Recommendation: only on demand. Brainstorming is divergent; the default startup flow is convergent.
2. **Should `@growth-marketer` replace the "growth" gap in the current `iterate` skill, or be a separate `growth` squad?** Recommendation: separate `growth` squad. Iteration is engineering; growth is go-to-market. Different skills, different people.
3. **Should `@legal-counsel` be added in T1 or deferred to T3?** Recommendation: deferred. Legal is jurisdiction-specific; getting it right is a research project, not a persona file. Defer to v2.1 when the team has time to actually consult a lawyer.
4. **Should we add a `@legal-counsel` for *privacy* (GDPR/CCPA) as a T2 persona?** Recommendation: yes, narrow scope, read-only. `@legal-counsel` (privacy) flags personal-data flows; doesn't draft legal text.
5. **Should the new `growth` squad include `@data-analyst`?** Recommendation: yes. Growth and analytics are inseparable.
6. **Should `@ml-ops` and `@ml-engineer` be one persona with a mode flag, or two separate personas?** Recommendation: two personas. The charters are non-overlapping (build the model vs. run the system around the model). One persona with a flag would have a 500-line charter.
7. **Should the `migration` squad be opt-in or default?** Recommendation: opt-in. Most projects never do a major migration. The cost of having 3 extra personas in `startup` is real.
8. **Should the new skills use the v1.5 step-file pattern, or the older single-file pattern?** Recommendation: step-file, always. The skills are getting longer; step-file is cheaper.
