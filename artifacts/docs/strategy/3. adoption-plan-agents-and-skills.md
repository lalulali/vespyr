# Vespyr Adoption Plan — Agents & Skills

> Status: Proposed for **v1.5** (next release after v1.4 *Continuous Improvement System*).
> Author: Vespyr core team, synthesized from a comparative review of **Vespyr v1.7.1**, **BMAD v6.8.0**, **Ruflo v3.14.0**, and **ECC v2.0.0**.
> Scope: This plan only covers the **agent library** and the **skill library**. Installer, harness adapters, and docs site are tracked separately in `ROADMAP.md`.

---

## 0. Why this plan exists

Vespyr already has a strong, opinionated foundation:

- 21 specialized agents with clear role separation.
- 23 skills as folder + `SKILL.md` (BMAD-compatible atomic unit).
- A 7-squad system for role curation.
- A file-based state machine (`orchestrator_state.js` + `pipeline-state.json`).
- A `memory-controller` that progressive-loads context to ~1,000 tokens.
- A `round-table` skill that already does **real subagent spawning** (BMAD's party-mode pattern, adopted early).
- A `delegation-pattern.md` that is the clearest articulation of the I/O separation in any framework.
- Multi-harness support across ~30 dotfolder targets.

The plan below does **not** propose a rewrite. It targets specific, well-scoped upgrades where BMAD, Ruflo, or ECC have objectively better patterns. Each section states: **what we adopt, what we explicitly do *not* adopt, and why**.

## 2. What we explicitly do **not** adopt

To prevent scope creep, the following patterns were considered and rejected:

| Pattern | Source | Why we don't adopt it |
|---|---|---|
| **Vector DB / HNSW / embeddings** | Ruflo AgentDB | Vespyr is deliberately file-based; we ship `memory_filter.js` keyword scoring. A vector store is a different category of system, not a layer on top. |
| **Plugin marketplace with 30+ plugins** | Ruflo | Out of scope; marketplace lives in `vespyr-modules/*` as v1.6 work. |
| **Federation / multi-node trust ladder** | Ruflo | Out of scope; vespyr is single-repo, single-machine. |
| **WASM neural runtime (SONA, EWC++, LoRA)** | Ruflo | Out of scope; vespyr does not ship model-fine-tuning hooks. |
| **10+ harness dotfolder mirroring with literal file copies** | BMAD | We use symlinks already. Symlink + thin shim is cheaper and battle-tested in our installer. |
| **`<workflow>` XML pseudo-DSL** | BMAD | Powerful but has a learning curve. We adopt the *folder + step files* structure but keep step bodies in plain Markdown. |
| **3-file TOML with 4-layer merge** | BMAD | Overkill for our 21 agents and 7 squads. We adopt a simpler 2-file split (defaults + project override). |
| **AIDefence 3-gate PII pipeline** | Ruflo | Out of scope; vespyr is a dev framework, not a production agent that handles PII. |
| **Strategic compaction env vars (`CLAUDE_AUTOCOMPACT_PCT_OVERRIDE`)** | ECC | Harness-specific. We expose progressive memory loading instead. |
| **12-locale README translations** | ECC | High effort, low value for v1.5. v1.7+ only. |
| **20+ language-specific reviewer agents** (typescript-reviewer, go-reviewer, …) | ECC | We adopt the *idea* (one reviewer per language family) as v1.6 work, not the 20-file inventory. |

The principle: **adopt the *idea*, not the inventory.** We do not want vespyr to look like BMAD v6.8 with different file names.

## 3. v2.0 — Agent & Skill upgrades

### 3.1 Skill as folder + micro-step files (BMAD)

**Today.** Every skill in `.agents/skills/<name>/SKILL.md` is a single file. `develop/SKILL.md` is 278 lines. `validate-idea/SKILL.md` is ~410 lines. The whole workflow — 9 numbered steps, prereqs, completion criteria, state machine integration — lives inline.

**Problem.** The LLM reads the whole file on activation, even when the user only wants to resume at step 6. Tokens are spent re-reading completed sections. The file becomes a wall of text that drifts over time.

**Adoption.** Skills become a **folder with a `SKILL.md` (the bootloader) + a `steps/` directory**. The bootloader tells the LLM to load `steps/step-01-*.md` on first activation, then jump to the step indicated by `stepsCompleted` in the output document's YAML frontmatter on re-activation.

```
.agents/skills/develop/
├── SKILL.md                       # 50–80 lines: bootloader + menu + state schema
├── customize.toml                 # 3-file customization (see 3.3)
├── steps/
│   ├── step-01-spec-review.md     # ~40 lines
│   ├── step-02-architecture.md
│   ├── step-03a-arch-spec-review.md
│   ├── step-03b-backlog-prep.md
│   ├── step-04-kanban-activation.md
│   ├── step-05-spike.md
│   ├── step-06-dev-loop.md
│   ├── step-07-quality-gates.md
│   ├── step-08-pm-verification.md
│   ├── step-09-documentation.md
│   └── step-10-completion.md
├── data/
│   └── role-tags.json             # { "FE": [...], "BE": [...], "Full-Stack": [...] }
└── templates/
    └── develop-state.md           # YAML state template for stepsCompleted
```

**Why this matters.**

1. **Token efficiency.** On re-activation, only the unfinished step loads. For a 9-step workflow that resumes at step 7, we save ~70% of the prompt.
2. **Maintainability.** Each step is a 30–80 line Markdown file. Reviewing, editing, or splitting a step is a tiny diff. We can ship step improvements without touching the rest.
3. **Resume semantics.** The `stepsCompleted` array in the output document's frontmatter makes resumption a deterministic operation. The LLM looks at the array, jumps to the right file, and continues.
4. **Phase gates are first-class.** Each step file declares its prerequisites as a `## Prerequisites` block. The `validate-idea` step can hard-gate on the existence of the founder brief; the `develop` step can hard-gate on the existence of `product-spec.md`.

**Why we don't adopt the `<workflow>` XML DSL.** BMAD uses `<step n="1" goal="...">`, `<action>`, `<check if="...">`, `<goto>`, `<ask>`, `<output>`, `<critical>`. It's powerful but adds a parsing layer the LLM must internalize. Plain Markdown is just as expressive when the step file is short, and humans can read it without a parser.

**Migration plan.** Convert these skills first (highest-token-burn, longest-files):
1. `develop` (278 lines, 9 steps)
2. `design` (similar shape)
3. `launch`
4. `validate-idea` / `validate-game-idea` (multi-step Socratic)
5. `incident` (triage → mitigate → RCA)
6. `explore-idea` / `explore-game-idea`

Skip these (already short or single-shot):
- `status`, `memory`, `phase`, `squad`, `kanban`, `help-me`, `humanize`, `review`, `test`, `plan`, `delegate`, `elicitation`, `grill-me`, `retro`, `iterate`, `round-table`, `code-graph`, `doc-graph`

**Effort.** ~3 days of work for the migration + ~1 day for the loader/compiler.

### 3.2 Spec-kernel + companions (BMAD)

**Today.** Vespyr's artifact templates (e.g. `prd-template.md`, 14KB) are long, prescriptive, and have stable section headers. Outputs follow the template; that is good, but they are also monolithic — the PRD is *the* PRD, no way to link out to a glossary, an architecture diagram, or a research artifact.

**Problem.** Long monolithic templates force the LLM to write 14KB of content even when 2KB is enough. A small feature's PRD looks identical to a platform's PRD.

**Adoption.** Adopt BMAD's **5-field spec kernel + content-typed companions** as the canonical artifact shape:

```
<artifact-folder>/
  SPEC.md                  # 5 fields: Why / Capabilities / Constraints / Non-goals / Success signal
  glossary.md              # content-typed companion
  user-journey.md          # content-typed companion
  acceptance-criteria.md   # content-typed companion
  .decision-log.md         # canonical memory for this spec
```

**Why this matters.**

1. **The 5-field kernel stays lean.** Every PRD is reduced to: *Why are we building this? What capabilities must it have? What constraints bind us? What are we explicitly NOT doing? How do we know we succeeded?* — and nothing else.
2. **Capability IDs are stable.** Each capability gets a `CAP-N` ID. Subsequent artifacts (architecture, user stories, tests) reference these IDs. The traceability is explicit.
3. **Companions are typed, not generic.** A `glossary.md` is different from a `user-journey.md`. The kernel doesn't try to be everything.
4. **The Spec Law (8 rules) becomes a self-validate sweep.** After writing the kernel, the skill runs an 8-rule check. Violations are fixed before handoff.

**Why we don't adopt BMAD's full Spec Law verbatim.** BMAD's rules are tight; ours can be lighter for the discovery / exploration phases where looseness helps.

**Migration plan.**
1. Add `templates/spec-kernel-template.md` (the 5 fields, ~50 lines).
2. Add `templates/spec-law.md` (8 rules, ~30 lines).
3. Update `prd-template.md` → split into `templates/prd/SPEC.md` (kernel) + `templates/prd/companions/` (glossary, acceptance-criteria, user-journey, decision-log).
4. Update `develop/SKILL.md` Step 1 to require the spec-kernel form.
5. Provide a `spec --distill` command on `@founder` and `@product-manager` agents: takes an existing long-form PRD and reduces it to the kernel.

**Effort.** ~2 days.

### 3.3 2-file customization TOML (BMAD-lite)

**Today.** Agent customization is done by editing the agent's `.md` file directly. There is no override layer, so a user's tweaks to `@developer` survive until the next `npx vespyr` upgrade, at which point they get overwritten.

**Problem.** We have no customization-vs-update story. Either users fork the agent (high friction) or they lose their tweaks on update (low trust).

**Adoption.** Adopt BMAD's **3-file contract**, simplified to 2 files (we don't need the per-user private layer because vespyr is committed to the repo):

```
.agents/agents/developer/customize.toml   # defaults (regenerated on update)
.agents/custom/developer.toml              # team-level override (committed, shared)
```

Merge rules — adopted verbatim from BMAD, simplified to 2 layers:

| Type | Rule |
|---|---|
| Scalars | override wins |
| Tables | deep merge |
| Arrays of tables where every item has `code` OR `id` | keyed merge (matching replace, new append) |
| All other arrays | append |

The merge is a single ~80-line script in `.agents/scripts/merge_customization.js`. Stdlib only (`fs`, `path`); we hand-write a minimal TOML parser (or vendor the BMAD Python resolver's logic as JS).

**Why we don't adopt BMAD's 3-file + 4-layer.** Two layers is enough for our commit-based workflow. The personal-override layer (`.user.toml`, gitignored) is only valuable for shared multi-user installs, which are not vespyr's target.

**Why this matters.**

1. **Customizations survive updates.** Project-level overrides are in `.agents/custom/`, not in the agent file. The installer regenerates the agent file; the override stays.
2. **Onboarding by example.** New users see `developer.toml` and learn the override surface by reading a real one.
3. **Cross-project portability.** The same agent file is identical across projects. Only the override changes.

**Migration plan.**
1. Add `.agents/scripts/merge_customization.js` (~80 lines).
2. Add `.agents/custom/.gitkeep` + a `.agents/custom/README.md` explaining the contract.
3. Add a `customize` skill at `.agents/skills/customize/SKILL.md` (a guided authoring flow — describe intent, get a valid TOML written).
4. Document the contract in `agent.md` / `AGENTS.md`.

**Effort.** ~2 days.

### 3.4 Frontmatter schema v2 (BMAD + ECC)

**Today.** The current frontmatter on agents is:
```yaml
description: ...
version: "X.Y"
last_updated: YYYY-MM-DD
human_name: ...
mode: subagent
temperature: 0.X
permission: { ... }
tools: { write: true, ... }
upstream_dependencies: [...]
downstream_consumers: [...]
```

This is good but missing fields that would unlock better tool/IDE integration.

**Adoption.** Add these fields to the schema:

```yaml
---
# v2 frontmatter — all fields required unless marked optional
name: developer                    # NEW: kebab-case, matches filename
description: ...                   # existing
version: "3.0"                     # existing
last_updated: 2026-05-19           # existing
human_name: Rex                    # existing
icon: 💻                           # NEW: emoji prefix carried in every response
mode: subagent                     # existing
temperature: 0.1                   # existing
permission: { ... }                # existing
tools: { write: true, ... }        # existing
model: opencode-go/claude-sonnet-4 # NEW: model hint
capabilities:                      # NEW: enumerated capability list
  - code-generation
  - refactoring
  - test-writing
upstream_dependencies: [...]       # existing
downstream_consumers: [...]        # existing
default_squad: build               # NEW: which squad(s) include this agent by default
origin: core                       # NEW: core | module:<name> for expansion packs
---
```

**Why this matters.**

1. **The `icon` field enables persona-prefixed responses** (see 3.10). Every reply starts with `💻 Rex: ...`. The user always knows which agent is in control.
2. **`capabilities` is a routing surface.** The `round-table` and `help-me` skills can match a user query against agent capabilities, not just descriptions. Better routing → less manual `@mention` fatigue.
3. **`default_squad` makes squad definitions redundant.** Today squads list agents by hand. With `default_squad` on agents, squads become *overrides* of the default membership, not parallel sources of truth.
4. **`origin: core | module:<name>`** is the v1.6 hook for expansion packs. Module agents are namespaced cleanly.
5. **`name`** is required for BMAD-compatibility — external tooling that parses our frontmatter expects it.

**Migration plan.**
1. Add a `.agents/scripts/validate_frontmatter.js` that enforces v2 schema.
2. Update all 21 agents with the new fields (one-time scripted migration).
3. Update `opencode.json` to consume `capabilities` for routing.
4. Update `compile_skills.js` to validate the new schema at install time.

**Effort.** ~1.5 days.

### 3.5 Lifecycle hooks with stable IDs (Ruflo + ECC)

**Today.** Vespyr has **zero** lifecycle hooks. The agent's only contract with the harness is the frontmatter and the markdown body. There is no `PreToolUse`, no `PostToolUse`, no `SessionStart`, no `PreCompact`.

**Problem.** We cannot enforce policy (e.g., "developer cannot delete files without confirmation") at the harness layer. We cannot run pre-flight checks. We cannot auto-save session state. We cannot auto-format on edit. We cannot auto-archive memory entries.

**Adoption.** Add a **hook graph** in `.agents/hooks/hooks.json`, with these events covered:

| Event | Hook ID | What it does |
|---|---|---|
| `SessionStart` | `session:start:load-context` | Auto-invoke `@memory-controller load` to surface the last session summary. |
| `SessionStart` | `session:start:detect-package-manager` | Detect npm/yarn/pnpm/poetry/cargo and surface in `project-context.md`. |
| `UserPromptSubmit` | `route:task` | Run a routing pass: classify the user query, suggest a squad or agent, surface the suggestion to the calling agent. |
| `PreToolUse` (Bash) | `pre:bash:safety` | Block destructive commands (`rm -rf /`, `diskutil eraseDisk`, `mkfs.*`, etc.) — the GUARDRAILS rules are enforced at the harness layer. |
| `PreToolUse` (Bash) | `pre:bash:tmux` | If a long-running test is launched, suggest tmux to free the main thread. |
| `PostToolUse` (Write\|Edit) | `post:edit:format` | Auto-format the edited file via the project's formatter (prettier, ruff, gofmt). |
| `PostToolUse` (Write\|Edit) | `post:edit:dedupe` | Run `@memory-controller dedupe-validate` on the last write to `artifacts/memory/`. |
| `Stop` | `stop:session-end` | Invoke `@memory-controller session-write` automatically. |
| `Stop` | `stop:check-console-log` | Warn if the change added a `console.log` (catches agent slip-ups). |
| `PreCompact` | `pre:compact:save-state` | Snapshot the current state machine + session before compaction. |
| `SubagentStop` | `subagent:stop:telemetry` | Emit a telemetry event to `artifacts/telemetry/`. |

Each hook has a **stable ID** like `pre:bash:safety` so users can disable selectively via env var:
```bash
VESPYR_DISABLED_HOOKS=pre:bash:tmux,stop:check-console-log
```

**Why this matters.**

1. **Enforcement at the harness layer.** GUARDRAILS.md is documentation today. Hooks turn it into a runtime contract. `rm -rf /` is blocked even if `@developer` somehow tries it.
2. **Less cognitive load on agents.** The agent doesn't need to remember to format, dedupe, or save state. The hooks do it.
3. **The pattern is the same as Ruflo and ECC.** Engineers coming from those systems recognize it instantly.
4. **Stable IDs + env var override is the right primitive.** ECC's `ECC_DISABLED_HOOKS=…` is the cleanest disable mechanism we saw.

**Why we don't adopt Ruflo's 27 hooks + 12 background workers.** That's the *Ruflo ceiling*. Vespyr's hook graph should be 8–12 hooks. Adding more is easy later; the cost of removing or rewriting a hook grows.

**Why we don't adopt Ruflo's "always exit 0" rule.** It's correct for hooks that learn / train (which we don't have yet). For our safety hooks, we want to be able to **block** an action — exit 2 to refuse.

**Migration plan.**
1. Add `.agents/hooks/hooks.json` with the 10 hooks above.
2. Add `.agents/scripts/hooks/*.js` — one Node script per hook.
3. Add a harness adapter in `bin/install.js` that writes the right hook config for Claude Code / OpenCode / Cursor.
4. Add `VESPYR_DISABLED_HOOKS` and `VESPYR_HOOK_PROFILE=minimal|standard|strict` env var support.
5. Document in `hooks/README.md`.

**Effort.** ~5 days (largest item in v1.5).

### 3.6 MCP tool surface (Ruflo + BMAD)

**Today.** `opencode.json` registers exactly one MCP plugin: `opencode-websearch-cited@1.2.0`. No first-party vespyr MCP. External tools (e.g., the round-table skill) cannot expose themselves as `mcp__vespyr__*` tools.

**Problem.** Our most valuable primitives — `@memory-controller load`, `@memory-controller write`, `orchestrator_state.js next`, `code-graph scan` — are buried inside skills. Other tools (e.g., an external dashboard) cannot call them. We are also blocking the install path for non-Markdown harnesses.

**Adoption.** Ship an **`@vespyr/mcp`** package that exposes the core primitives as MCP tools. The package is a thin Node.js server (stdio transport, JSON-RPC) that wraps the existing scripts.

```typescript
// mcp__vespyr__memory_load — wraps memory_filter.js
mcp__vespyr__memory_load({
  agent: "developer",
  task: "implement auth login flow",
  tier: "balanced"  // "core" | "balanced" | "full"
}) → { context: string, tokens: number, sources: string[] }

// mcp__vespyr__memory_write — wraps the dedupe-validate + append flow
mcp__vespyr__memory_write({
  file: "patterns-and-conventions.md",
  entry: "### [CODE] ..."
}) → { ok: boolean, deduped: boolean, id: string }

// mcp__vespyr__pipeline_status — wraps orchestrator_state.js status
mcp__vespyr__pipeline_status() → { phase: string, next: string, missing: string[] }

// mcp__vespyr__pipeline_next
mcp__vespyr__pipeline_next() → { action: "advance-phase" | "generate-artifacts", required: string[] }

// mcp__vespyr__code_graph_scan
mcp__vespyr__code_graph_scan({ path: "src/" }) → { nodes: number, edges: number, hotspots: string[] }

// mcp__vespyr__code_graph_query
mcp__vespyr__code_graph_query({ symbol: "auth.login" }) → { callers: string[], callees: string[] }

// mcp__vespyr__elicitation_methods
mcp__vespyr__elicitation_methods({ count: 5, context: "PRD section" })
  → { methods: [{ name, description, output_pattern }] }

// mcp__vespyr__squad_list
mcp__vespyr__squad_list() → { squads: [{ name, agents, description }] }

// mcp__vespyr__squad_switch
mcp__vespyr__squad_switch({ squad: "build" }) → { ok: boolean, active: string }

// mcp__vespyr__agent_resolve
mcp__vespyr__agent_resolve({ query: "who reviews PRs" }) → { agent: "code-reviewer", confidence: number }
```

**Why this matters.**

1. **External tools can use vespyr.** A future Vespyr dashboard, a CI bot, a VS Code extension — all can call the same primitives as the agent.
2. **The agent ↔ primitive boundary gets explicit.** Today the agent invokes `@memory-controller` and the LLM figures out the right call. With MCP, the call is typed and the response is structured.
3. **It de-risks the v1.6 expansion-pack work.** Modules are easier to write when they can call shared primitives via MCP, instead of re-implementing the same logic.
4. **Pattern consistency with Ruflo and BMAD-CIS.** Both ship MCP tools. Users coming from those systems expect them.

**Why we don't adopt Ruflo's 314-tool scale.** That's the *Ruflo ceiling* again. Our 10 tools cover the 90% of useful operations. Adding more is a 1-day script per tool.

**Why we don't adopt the binary RVF memory format.** It's powerful but opaque. Vespyr's memory is *legible* Markdown. We can add a binary cache layer later without changing the source-of-truth files.

**Migration plan.**
1. Add `packages/mcp/` to the vespyr monorepo.
2. Implement the 10 tools as thin wrappers around the existing scripts in `.agents/scripts/`.
3. Add the package to `opencode.json` `mcp` block by default.
4. Add an `npx vespyr mcp start` command.
5. Update agents to use the MCP tools directly when available (e.g., `@memory-controller` becomes optional; the agent can call `mcp__vespyr__memory_load` directly).

**Effort.** ~4 days.

### 3.7 Status YAML layered on `pipeline-state.json` (BMAD)

**Today.** `orchestrator_state.js` reads and writes `artifacts/output/pipeline-state.json`. The schema is implicit; the script owns it.

**Problem.** The state machine is *in the script*. Other tools (e.g., a dashboard, a CI check, a custom agent) cannot read or write state without calling the script. There is no explicit, human-readable state schema.

**Adoption.** Add a **`artifacts/output/sprint-status.yaml`** as a parallel, human-readable state artifact (BMAD's pattern). The state machine script reads from it on `status` and `next`, and writes to it on `complete`.

```yaml
# artifacts/output/sprint-status.yaml
generated: 2026-06-24
last_updated: 2026-06-24
project: vespyr
project_key: vespyr
tracking_system: file-system
squad: build
phase: development

# Phase-level status
phases:
  discovery: done
  exploration: done
  strategy: in-progress
  architecture: backlog
  development: backlog
  quality: backlog
  launch: backlog

# Story-level status (when in development)
stories:
  US-001-user-auth: done
  US-002-account-management: in-progress
  US-003-plant-data-model: backlog
```

**Why this matters.**

1. **Human-readable state.** A PM can read `sprint-status.yaml` in any text editor and see the project at a glance. JSON state is opaque.
2. **CI integration.** A CI job can grep for `phases.development: in-progress` and gate releases. With JSON, you have to parse.
3. **Cross-tool portability.** The YAML is a stable contract. The script's internal state can change; the YAML schema is frozen.
4. **Story-level status mirrors BMAD.** When we're in development, every user story has a status. `sprint-status.yaml` becomes the source of truth for "what's ready for dev" → "what's in progress" → "what's done".

**Why we don't adopt BMAD's full status lifecycle verbatim.** We add a phase-level layer that BMAD doesn't have (it assumes you're past the strategy phase). Vespyr's lifecycle is longer.

**Migration plan.**
1. Define the YAML schema in `templates/sprint-status-template.md`.
2. Add `read` / `write` helpers to `orchestrator_state.js` for the YAML file.
3. Update the script's `status` and `next` commands to read from the YAML.
4. Add a `sprint-status` skill to render the YAML as a Kanban.

**Effort.** ~1.5 days.

### 3.10 Icon-prefixed persona (BMAD)

**Today.** Agents have a `human_name` (e.g., "Rex") but no `icon`. Responses do not prefix the agent's identity. When the user sees 8 paragraphs of agent output, they don't know which agent spoke.

**Adoption.** Every agent declares an `icon: 💻` in frontmatter (added in 3.4). Every agent's first line of every response prefixes with `<icon> <human_name>:`. E.g.:

> 💻 **Rex:** I'll start by reading the spec at `artifacts/output/02-strategy/product-spec.md`...

**Why this matters.** This is a trivial change with outsized UX impact. BMAD does it, and once you see an icon-prefixed conversation you can't go back. Users always know which persona is in control.

**Why we don't adopt BMAD's full icon-as-character rule.** BMAD uses the icon as a literal character that *carries through every turn* in a session. We approximate with a prefix line — the LLM is reliable at prefixing, less reliable at remembering to put the icon mid-response.

**Migration plan.** Single pass through all 21 agent files. Add `icon:` field. Add a "Begin every response with `{icon} {human_name}:`" instruction to each agent's body.

**Effort.** ~2 hours.

---

### 3.11 Hardcoded identity (BMAD)

**Today.** Agent identity is in frontmatter (`human_name`, `description`) and is freely editable. A user can rename `@developer` to `@bob`.

**Adoption.** Split agent identity into two surfaces:
- **Hardcoded identity** (not customizable): `name`, `icon`, the persona's *core* (e.g., "I am a senior software engineer with TDD discipline").
- **Customizable behavior** (overridable via `.agents/custom/<agent>.toml`): principles, capabilities, persistent facts, communication style.

In the agent file, hardcode the core identity at the top with a clear `<!-- IDENTITY: do not edit -->` block. The customizable surface lives below it.

**Why this matters.** Without this split, customization destroys identity. With it, `@developer` is *always* `@developer` — the senior software engineer persona — but every project's `@developer` is tuned to that project's stack and conventions.

**Migration plan.** Update all 21 agent files with the `<!-- IDENTITY: do not edit -->` block. Update the customize skill (3.3) to enforce that overrides can only touch fields *below* the identity block.

**Effort.** ~1 day.

---

## 4. v1.6 — Optional / larger adoptions

These are recommended but not v1.5-critical. They can ship in v1.6.

### 4.1 Language-specific rules with CSS-like specificity (ECC)

**Adoption.** Add `.agents/rules/` with a `common/` floor and per-language overrides:

```
.agents/rules/
├── common/
│   ├── coding-style.md
│   ├── testing.md
│   ├── git-workflow.md
│   └── ...
├── typescript/
├── python/
├── go/
└── ...
```

The merge priority is: language > common. A `rules/python/testing.md` overrides `rules/common/testing.md` for Python projects. This is the **exact pattern** ECC uses and it works.

**Why this matters.** Vespyr agents today write code in 1–2 languages per project. With language-specific rules, `@developer` automatically follows that language's idioms (Python prefers pytest, Go prefers table tests, TypeScript prefers Vitest). It's the cheapest way to make agents feel like native speakers of the stack.

**Effort.** ~3 days.

---

### 4.2 Module / expansion-pack model (BMAD)

**Adoption.** External modules become separate npm packages (`vespyr-module-game-studio`, `vespyr-module-ml-pipeline`, etc.). Each module has its own agents, skills, templates, and a `module.yaml` schema that the installer understands.

```
vespyr-module-game-studio/
├── module.yaml          # name, version, depends-on, agents, skills
├── agents/
├── skills/
└── templates/
```

The installer reads `module.yaml` and merges the module's content into the target project. Updates are versioned per-module.

**Why this matters.** The `game-studio` squad, the `ml-engineer` agent, and the `validate-game-idea` skill are not core to most users. Today they ship anyway. With modules, the core `vespyr` package stays lean (~15 agents, ~15 skills), and domain-specific extras opt in.

**Why this is v1.6, not v1.5.** The installer needs to support module resolution first (ROADMAP v1.2 / v1.3 work). Modules build on top of that.

**Effort.** ~1 week.

---

### 4.3 Skill-builder / agent-builder skills (BMAD)

**Adoption.** Add three meta-skills that eat vespyr's own dog food:

- `.agents/skills/agent-builder/` — guides the user through creating a new agent persona (name, icon, principles, capabilities, permissions).
- `.agents/skills/skill-builder/` — guides the user through creating a new skill (folder + SKILL.md + steps/).
- `.agents/skills/workflow-builder/` — guides the user through creating a multi-agent workflow (which agents, in what order, with what gates).

Each builder uses the **same** scaffolding the installer uses internally, so a hand-written skill is byte-identical to an installer-generated one.

**Why this matters.** Today, adding a new skill means hand-editing 4 files. A guided builder makes the cost of adding a domain-specific skill (e.g., `@solidity-engineer`, `@ios-developer`) ~5 minutes.

**Effort.** ~1 week.

---

### 4.4 Witness / verification harness (Ruflo)

**Adoption.** A minimal witness system: a `verification/manifest.json` listing every documented fix (issue ID, file, marker substring, OS). A `verification/verify.mjs` script re-checks the file is in its expected state. A `verification/history.jsonl` records each run for bisect.

**Why this matters.** As the installer grows (v1.2+), the chance of a silent regression grows. A witness system catches them before users do.

**Why v1.6.** The installer needs to be more mature first. v1.5 is too early.

**Effort.** ~1 week.

## 7. Risk register

| Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|
| Micro-step files drift from the bootloader | Medium | Medium | The bootloader enforces state via `stepsCompleted`; the loader script (3.1) validates file presence. |
| Hooks break in Claude Code / OpenCode | Medium | High | Each harness gets a per-harness adapter; CI runs against all 3 harnesses. |
| MCP tools become a second source of truth | Low | High | The MCP tools are *wrappers* around existing scripts, not replacements. The script is the truth. |
| Frontmatter v2 migration breaks external parsers | Low | Low | v1 fields are still allowed (deprecated). v2 is opt-in for the first 30 days. |
| Spec-kernel is too thin for some artifacts | Medium | Low | The kernel is the *minimum*; agents can write additional sections, but they live in companion files, not the kernel. |
| Module model delays v1.6 | Medium | Low | v1.5 ships without modules; v1.6 is a separate release. |

## 8. Open questions

1. **Should the spec-kernel replace the PRD template entirely, or coexist?** Recommendation: coexist for one release, then deprecate the long PRD template in v1.6.
2. **Should the `sprint-status.yaml` be the *only* state, or a parallel read-only mirror of `pipeline-state.json`?** Recommendation: mirror for v1.5, single-source-of-truth in v1.6 when we add the writer.
3. **Should hooks be opt-in (default off) or opt-out (default on) for safety hooks?** Recommendation: safety hooks always on; format/quality hooks opt-out via env var.
4. **Should MCP tools be enabled by default in `opencode.json`?** Recommendation: yes for the 10 core tools; users can disable per-tool.
