## Part 1 — Strategic Themes

The v2.0 work is organized into **6 themes**. Every file in the inventory maps to exactly one theme. Themes are *capability-shaped*, not implementation-shaped — they describe what vespyr becomes, not how the work is sequenced.

| # | Theme | One-line statement |
|---|---|---|
| **T1** | **Agent depth** | Agents are *role-locked* personas, not editable prompts. Customization is structured and survives updates. |
| **T2** | **Skill atomicity** | A skill is a *folder of self-contained step files*, not a single Markdown blob. Skills resume; skills have phases; skills are first-class tools. |
| **T3** | **Artifact rigor** | Every artifact has a kernel + companions, a status, a hash witness, and a traceability graph. Nothing is silent. |
| **T4** | **Harness contracts** | Vespyr enforces policy at the harness layer (hooks), exposes its primitives to other tools (MCP), and ports cleanly across IDEs. |
| **T5** | **Self-improvement loop** | Sessions leave behind patterns. Patterns promote to conventions. Conventions promote to instincts. Instincts auto-load. |
| **T6** | **Modularity** | The core stays lean. Domain extras (game, ML, security, finance) ship as separate packages. Selective install is the default. |

These themes compose: T1 makes T2 worth doing (rigorous agents benefit from atomic skills). T2 + T3 enable T4 (the harness can trust the artifacts). T4 enables T5 (hooks can auto-extract patterns). T5 + T6 mean a project gets smarter over time, and adding a new domain doesn't bloat the core.

| **Ruflo — Federation WSS + WireGuard mesh** | Out of scope; single-machine only. |

**Principle:** adopt the *idea*, not the *inventory*. We do not want vespyr to look like BMAD v6.8 with different file names.

## Part 5 — Risk Register

| Risk | Likelihood | Impact | Mitigation | Owner |
|---|---|---|---|---|
| Step-file split loses content from the current monolithic SKILL.md | Medium | High | Use a content-audit script before the split: assert that every section in the old SKILL.md has a home in the new files. | Phase 1 |
| Tri-modal mode detection misfires (user says "validate" but the LLM runs "create") | Medium | Medium | The first read of the SKILL.md is a *literal mode selector*; the LLM cannot skip it. Test with adversarial prompts. | Phase 1 |
| Hooks break in Claude Code / OpenCode / Cursor | Medium | High | Per-harness adapter in `bin/install.js`; CI runs against all 3 harnesses. Safety hooks must `exit 0` by default and `exit 2` only for explicit safety events. | Phase 2 |
| MCP tools become a second source of truth | Low | High | MCP tools are *wrappers* around existing scripts. The script is the truth. MCP never owns state. | Phase 2 |
| `witness.js` false positives (legitimate edits trigger `[INTEGRITY-WARNING]`) | Medium | Medium | Re-sign on every `@memory-controller write`; the witness is a *history*, not a *lock*. The first integrity warning is informational. | Phase 2 |
| Self-learning promotes false patterns too aggressively | Medium | High | 3+ occurrences, 2+ agents, 7+ day span is *all required*. Every promotion is human-in-the-loop. The `instincts.md` file is opt-in: if you don't want auto-load, don't promote. | Phase 2 |
| Graph auto-build adds 2-5s latency to every skill | Low | Medium | `auto_graph.js check` is mtime-only (no parsing); runs in < 500ms. `build` only runs when `[STALE]`. | Phase 3 |
| Catalog parity test fails on first run (counts already off) | High | Low | This is *expected* on first run. The test outputs the diff and exits 1; the v2.0 release is the fix. | Phase 3 |
| Module split breaks existing installs | Low | High | `install-modules` is opt-in. Default install matches current behavior. The `core` module is always required. | Phase 4 |
| Frontmatter v2 migration breaks external parsers | Low | Low | v1 fields still allowed (deprecated). v2 enforced at v2.0 release; v1 fields removed at v3.0. | Phase 0 |
| Spec-kernel too thin for some artifacts (LLM skips the kernel) | Medium | Low | Kernel is the *minimum*; agents can write additional sections, but they live in companion files, not the kernel. The `spec-law` self-validate sweep catches it. | Phase 1 |
| Icon-prefix instruction not followed by the LLM | Low | Low | Trivial; reinforced at session start via `@memory-controller` Step 0.5 instruction injection (Phase 3 telemetry). | Phase 0 |
| Total time overruns the 8-week estimate | Medium | Medium | Each phase is independently shippable. If Phase 3 slips, ship Phases 0–2 as v2.0 and defer Phase 3 to v2.1. | All phases |

## Part 6 — Definition of Done

The v2.0 release ships when **all 14 criteria** are met:

1. **All 21 agents have v2 frontmatter** — `name`, `icon`, `channeled_mentor`, `capabilities`, `default_squad`, `origin`, plus a `<!-- IDENTITY: do not edit -->` block. `validate_frontmatter.js` exits 0 on all 21.
2. **The 5 skills are folder + step files** — `develop` (9 steps), `validate-idea` (tri-modal, 7+5+5 steps), `retro` (5 steps), `design` (tri-modal, 6+4+4 steps), `launch` (5 steps). Each `SKILL.md` is ≤ 60 lines and is a *router*, not a *content blob*.
3. **Resume semantics work** — re-activating a skill with `stepsCompleted: [1,2,3,4,5]` jumps to step 6, not step 1. Verified by a test that runs each skill against a fixture.
4. **Spec-kernel is the canonical PRD shape** — `templates/prd/SPEC.md` + `templates/prd/companions/` exist; `prd-template.md` is removed. The develop skill requires the kernel form in Step 1.
5. **10 lifecycle hooks are registered, env-var-disablable, and documented** — `VESPYR_DISABLED_HOOKS` and `VESPYR_HOOK_PROFILE` work; `hooks/README.md` lists all 10 IDs.
6. **MCP tool surface exposes 10 tools** — `mcp__vespyr__memory_load`, `memory_write`, `pipeline_status`, `pipeline_next`, `code_graph_scan`, `code_graph_query`, `elicitation_methods`, `squad_list`, `squad_switch`, `agent_resolve`. All 10 are callable from a Claude Code or OpenCode session.
7. **`sprint-status.yaml` is the human-readable state** — `orchestrator_state.js status` and `next` read from it; `complete` writes to it.
8. **QA is a hard gate** — `orchestrator_state.js next` refuses to advance out of `development` without `qa-signoff.md` containing `Release recommendation: GO|CONDITIONAL`.
9. **Self-learning works end-to-end** — `node .agents/scripts/self_learn.js scan-episodes --since=30d` runs without error on the Vespyr project's own `artifacts/memory/`; `instincts.md` is loaded FIRST by `@memory-controller`.
10. **Graph is auto-built at 5 lifecycle moments** — session start, `/design` sign-off, `/develop` Step 3, `/retro` Step 1, `orchestrator_state.js complete`. `auto_graph.js check` runs in < 500ms.
11. **Catalog parity test passes** — `npm test` includes `test_catalog_parity.js` and exits 0. README says 21 agents, 23 skills, 7 squads, 76 new files — on-disk reality matches.
12. **A new user can run `npx vespyr init --example` and get a working project in 30 seconds** — the example project is a CLI todo list with all 10 phase folders populated and cross-references intact.
13. **The visual spec companion (`design.md`) and dynamic HTML presentation** are generated by `@product-designer` (Ivy) adaptively based on Rigid vs. Creative style combinations, with the 56KB static HTML template deleted (3.2.1).
14. **The orchestrator status and next CLI dashboards** output beautiful human-readable ASCII tables by default when run in terminal, and agents enforce pipeline state checks at startup and shutdown (3.7.1).

## Part 7 — Open Questions for the Next Planning Cycle

These are the questions this plan does *not* answer. They are explicitly deferred to v2.1+ planning.

1. **Should `install-modules` ship as a v2.0 feature, or is the `core` + opt-in enough?** (Recommend: ship as v2.0, even if it's a single-tenant `install-modules.json`; the multi-tenant `vespyr-module-*` packages are v3.0.)
2. **Should the spec-kernel replace the PRD template entirely, or coexist?** (Recommend: replace, with a deprecation notice for the long PRD in v2.1.)
3. **Should `sprint-status.yaml` be the *only* state, or a parallel read-only mirror of `pipeline-state.json`?** (Recommend: YAML is the source of truth from v2.0; `pipeline-state.json` becomes a derived cache written on every YAML change.)
4. **Should hooks be opt-in (default off) or opt-out (default on) for safety hooks?** (Recommend: safety hooks always on; format/quality hooks opt-out via env var.)
5. **Should MCP tools be enabled by default in `opencode.json`?** (Recommend: yes for the 10 core tools; users can disable per-tool via `VESPYR_DISABLED_MCP=code_graph_scan,elicitation_methods`.)
6. **How do we handle the `humanize` skill long-term?** (Recommend: vendor it with attribution for v2.0, plan a native replacement for v2.1 or v2.2.)
7. **Do we ship `vespyr-module-game-studio` as the first expansion pack?** (Recommend: yes, in v2.1; it validates the module model on the most-requested use case.)
8. **Should the `channeled_mentor` references be enforced at install time, or just documented?** (Recommend: documented; enforcement is a v3.0 personality-lint feature.)
9. **What goes into the v3.0 backlog?** (Initial list: multi-agent parallelism via git worktrees, MCP server-as-tool for external integration, agent marketplace, VS Code extension, Vespyr Cloud for shared team memory, multi-locale docs, 20+ language-specific reviewer agents, WDS-style persona handoff for multi-session projects.)
10. **Is the 8-week estimate too aggressive or too conservative for a solo maintainer?** (Estimate is for a focused 1-person effort at 15 hours/week. If 2 contributors can split, halve the time. If only 5 hours/week available, double the time.)

- After Phase 0: vespyr is "rigorous" (agents locked, customization works, entry points consolidated).
