# Step 2 — Write the plan

Create an immutable draft revision using the required field and section checklist below. Write exactly one new plan file beneath the artifact root returned by Step 0; do not edit inputs or write any other repository path.

## Establish revision identity

- If no plan revision exists in this run root, use `planId: MP-001` and `planRevision: 1`.
- If exactly one plan ID exists, preserve it and increment its revision. Write a new revision file; do not overwrite the prior one.
- If plan IDs or revision history conflict, stop and ask the repository owner which record is authoritative.
- Record the exact full `baseRevision` and `workingTreeIdentity` supplied by the caller or by an evidence record under the external state root. If either is unavailable, stop; do not inspect the rest of the checkout to reconstruct them.
- The `dirtyManifest` identity field holds the machine-readable per-file fingerprints for the plan's relevant paths. It is generated by the documented manifest command in the "Generate the dirty manifest" section below, never hand-written.
- Compute `planDigest` as SHA-256 over the plan content after replacing the `planDigest` field value with the literal `[DIGEST OMITTED]`. Record the canonicalization rule. Any content change requires a new revision and digest.

Use this path pattern:

```text
artifacts/output/maintenance/<run-id>/maintenance-plan-<plan-id>-r<revision>.md
```

## Required plan content

The plan must start with one plain sentence and include:

1. **Identity:** `runId`, `planId`, `planRevision`, `planDigest`, full `baseRevision`, complete `workingTreeIdentity`, the generated `dirtyManifest`, canonical `externalStateRoot`, exact `repoArtifactRoot`, creation date, author, and `recordStatus: DRAFT`.
2. **Scope:** explicit in-scope work, out-of-scope work, assumptions, constraints, and links to the maintenance inputs. State that this is a closeout plan only; it does not execute code changes or establish gate-green.
3. **Input reconciliation:** all five required inputs, IDs and local links checked, inherited/unverified source references, and any limitations.
4. **Findings:** unique ID, claim/provenance, current status, accountable owner, decision owner where relevant, exact source links, exact test/verification references, evidence references, revision covered, and blockers. Never turn absent evidence into a pass.
5. **Open owner decisions:** keep B1, O-4, B10, and `credential-residual` `[OPEN]`; list the exact question, owner, dependent work/gate, and `OPEN — no disposition recorded`. Do not create estimated tasks to make these choices or choose an owner policy.
6. **Task table:** every planned task is 1–4 hours and has a concrete first action, observable done evidence, status, owner, decision owner or reason for none, exact source links, trace IDs (`US-###`/`AC-*` where applicable), verification, task and decision dependencies, and parallel tasks. Do not treat an owner decision as an estimated work item.
7. **Dependency graph:** use Mermaid. It must contain every task-to-task dependency from the task table and every open-decision-to-task blocking edge, with no extra or missing edges. The direction is prerequisite → dependent task; use dashed edges for decision blockers.
8. **Parallelism:** list symmetric parallel groups and why there is no dependency path or shared-resource conflict. Do not allocate worktrees or invoke worktree helpers.
9. **Verification:** for each code task, identify an exact existing behavior test or a specifically named test to add, its file and command, and how it passes with the fix but fails when the fix is reverted. If that cannot be supported from the allowed inputs, add a bounded discovery task first and keep the dependent implementation out of the ready task list. For each non-code task, specify manual steps, expected and observed result, verifier, date, and revision.
10. **Risk register:** name each risk, likelihood, impact, mitigation, owner, and trigger/evidence. Include source-reference staleness, unresolved owner decisions, revision drift, and any unverified task estimate.
11. **Separate review records:** technical review by `@tech-lead` and repository-owner execution authorization as distinct records, each tied to the same run, plan ID, revision, digest, exact scope, date, and evidence reference. Mark absent records `PENDING`.
12. **Checker status:** record the result of the documented plan-check command below. Do not claim a plan check passed unless that command was actually run against this exact revision and its raw result is referenced.

### Task sizing and blockers

- Break work down until each executable task is 1–4 hours. If a task cannot be estimated in that range from the allowed evidence, split it or keep it blocked pending a bounded discovery task; do not round it up.
- A task's first action names the first exact file, command, or record an authorized executor will inspect or change. Its done evidence names the observable result and where it will be retained.
- Do not estimate the time required for an owner decision. Put choices in the open-decision table. If a decision-dependent work scope cannot be bounded without choosing a policy, list it as unplanned/blocked scope with no task ID or estimate until the owner rules.
- Keep inherited code/test references labelled unverified. The executor must confirm current paths and behavior after separate authorization; this planning skill does not read them.

## Generate the dirty manifest

The relevant-path set is derived from the plan itself — the Findings source/test/evidence cells, the Task list source and verification cells, the run-root paths in the Inputs table, and the repository source references list. The manifest therefore has to be generated **after** those tables exist and **before** the digest is frozen.

Run the documented manifest command against the plan file you just wrote:

```sh
node .agents/scripts/maintenance_plan_check.js manifest \
  --scope maintenance \
  --repo-root <absolute-repository-root> \
  --state-root <caller-supplied-absolute-external-root> \
  --run-id <run-id> \
  --plan <absolute-plan-path> \
  --json
```

The command is read-only: it writes nothing, and it changes no file, index, or state root. It prints six keys:

- `valid` — `true` when the manifest was computed with no issues, `false` when one was found.
- `manifest` — the object to paste into the `dirtyManifest` identity field: `schema` `dirty-manifest-v1` and a `files` array whose entries carry exactly `status`, `path`, `kind`, `mode`, and `contentSha256`, sorted by normalized path and then status.
- `relevantPaths` — the paths the manifest covers. Read this list back: it is the plan's own claim about which files are in scope.
- `planDigest` — the digest of the plan bytes as they stand at that moment.
- `issues` — every problem found while deriving the manifest, each with a `code` and a `message`; empty when `valid` is `true`. An issue here means the manifest is not usable — fix the cause and run the command again.
- `executionAuthorized` — always `false`. The manifest command never authorizes execution.

Rules for writing the field:

- Paste the `manifest` object as **one single-line JSON object** in the `dirtyManifest` identity cell. Do not reformat it, reorder its keys, round-trip it through a different schema, or edit any fingerprint by hand.
- The plan file itself is excluded from the relevant set, so pasting the manifest does not change the manifest. It does change the plan bytes, and therefore the digest.
- Recompute `planDigest` after the manifest is written into the plan, using the canonicalization rule above, and update the `planDigest` field.
- A clean relevant set is an empty `files` array. That is a valid manifest, not a missing one.
- If the command reports issues, or exits non-zero, do not paste anything. Fix the referenced plan problem first — a forbidden product-state or non-allowlisted path reference, an unsupported path kind, or an unreadable path — and re-run the command.
- Do not paste a manifest you did not just generate, and do not paste a manifest from an earlier revision of the plan.

**Fail closed on a stale or mismatched manifest.** A plan whose `dirtyManifest` no longer matches the computed fingerprint for its relevant paths is invalid, even when every other field is complete. The plan check reports this as a mismatch, a missing entry, or an extra entry. The fix is to regenerate the manifest with the documented command, recompute the digest, and re-run the check. Never patch the manifest by hand to make a check pass, and never drop a changed relevant path from the manifest.

## Run the plan check

With the manifest and digest in place, run the documented plan-check command against the same file:

```sh
node .agents/scripts/maintenance_plan_check.js check \
  --scope maintenance \
  --repo-root <absolute-repository-root> \
  --state-root <caller-supplied-absolute-external-root> \
  --run-id <run-id> \
  --plan <absolute-plan-path> \
  --json
```

It writes nothing. It validates one draft plan and reports `valid`, `planStatus`, and an `issues` array.

- The checker validates **draft** plans only. `recordStatus` must be `DRAFT`, and it stays `DRAFT` for the plan's whole life — including after the owner authorizes it. Authorization is recorded in the review/authorization rows and in external maintenance state, never by changing the status field.
- The checker's output always carries `executionAuthorized: false`. It never authorizes execution, never approves a plan, and never emits a gate verdict. A passing check is a **recorded claim about one exact revision**, not authorization.
- A failing or missing check means the plan is not review-ready. Fix the reported issues in a new revision; do not describe an unchecked plan as checked.
- If the plan file changes after the check — including the paste of a regenerated manifest — the check result belongs to the old bytes. Re-run it against the final bytes and re-record the result.

## Freeze and record the draft

After all required fields and tables are complete, the manifest is generated and pasted, the digest is recomputed, and the check has actually run — freeze the file and record:

```sh
node .agents/scripts/maintenance_state.js event --scope maintenance --repo-root <absolute-repo-root> --state-root <caller-supplied-absolute-external-root> --run-id <run-id> --type plan_drafted --details-json '{"planId":"<plan-id>","planRevision":"<revision>","planHash":"sha256:<digest>","artifactPath":"artifacts/output/maintenance/<run-id>/maintenance-plan-<plan-id>-r<revision>.md","recordStatus":"DRAFT","claimStatus":"recorded-claim"}' --agent <agent> --session-id <session-id>
```

The state store reads the plan identity from `planId`, `planRevision`, and `planHash`. `planHash` carries the plan's `planDigest` value verbatim, and `planRevision` carries the plan's revision as the same string the plan file records. A detail set missing one of those three keys is stored as an invalid plan event, so the later authorization, execution, and verification records will not chain to this draft.

Then check `maintenance_state.js status` for the same run. Event and status are records, not authentication. Keep the plan file unchanged after review; any edit creates a new revision with a new digest, invalidates earlier review/authorization for the old digest, and requires a fresh technical review and a fresh owner authorization bound to the new revision and digest. The plan file's `recordStatus` stays `DRAFT` in every revision.

**Step 2 is complete** when the immutable plan revision exists under the exact run root, its `dirtyManifest` holds the generated JSON, its digest was recomputed after that JSON was written, the documented check command actually ran against those final bytes, and its identity and evidence references are recorded externally. No execution begins.
