# Product Metrics Frameworks

Reference document for the `@product-manager` agent. Load this file when defining success metrics, validating measurement plans, or auditing existing metrics for vanity bias.

---

## 0. North Star Metric (NSM)

The North Star Metric is the single metric that best captures the core value your product delivers to users. It is the top node of every Drivers Tree and the anchor for all GSM blocks. Every other metric in the plan should either *drive* or *guard* the NSM.

> **Rule:** One product area = one NSM. If you cannot identify a single NSM, the product scope is too broad.

### What a Good NSM Measures

A meaningful NSM must sit at the intersection of three properties simultaneously:

```
          User Value
              ▲
              │
              │   ← NSM lives here
              │
 Business ◄───┼───► Product Engagement
  Revenue
```

| Property | Definition | Failure if missing |
|----------|-----------|--------------------|
| **User Value** | Reflects that users are getting a real outcome from the product | NSM rises even when users aren't benefiting (e.g., raw session count) |
| **Business Revenue** | Correlates with the business model's long-term health | NSM is disconnected from how the company actually makes money |
| **Product Engagement** | Captures repeated, intentional product use — not passive or accidental | NSM can be gamed or inflated by notifications, dark patterns, or external events |

### NSM Selection Criteria (the Five Tests)

Run every NSM candidate through all five before accepting it:

| # | Test | Pass condition |
|---|------|----------------|
| **1. The Value Moment Test** | Does this metric fire at or just after the moment a user receives the core product value? | ✅ Yes — it is downstream of the "aha moment" |
| **2. The Frequency Test** | Does this metric occur often enough to be measurable and actionable within a sprint cycle? | ✅ Weekly or more frequent |
| **3. The Leading Indicator Test** | Does a rise in this metric *predict* future revenue or retention, not just confirm past activity? | ✅ Has a demonstrated or logical causal link to retention/revenue |
| **4. The Team Alignment Test** | Can every squad (engineering, design, data, marketing) trace their work back to moving this number? | ✅ Yes — no squad is irrelevant to it |
| **5. The Anti-Vanity Test** | Would a 20% rise in this metric force a meaningful product decision? | ✅ Yes — it is not a raw count or a feel-good number |

### Four NSM Traps to Avoid

| Trap | Example | Why It Fails |
|------|---------|-------------|
| **Activity trap** | "Total sessions per month" | Counts presence, not value — a broken product with a spinner still logs sessions |
| **Revenue trap** | "Monthly revenue" | Lags too far behind product changes; hides *why* revenue is moving |
| **Acquisition trap** | "New signups per week" | Ignores whether users stay and get value; optimizes the top of funnel only |
| **Breadth trap** | "Total features used" | A user clicking everything randomly scores the same as a power user |

### How to Define Your NSM: Four Questions

Work through these questions in order. Each answer narrows the candidate pool:

**Q1. Who is your primary user, and what outcome do they want?**
> Focus on the job-to-be-done, not demographics.
> *Example: "A developer who wants their agent swarm to ship a feature without manual coordination."*

**Q2. What is the single moment when that user knows they got value from your product?**
> This is the "value moment" or "aha moment" — the NSM should fire at or just after this.
> *Example: "When the first output artifact is generated by a skill workflow."*

**Q3. How often does a healthy, retained user experience that value moment?**
> This determines the right time window (daily, weekly, monthly).
> *Example: "Power users run 3–5 skills per week; casual users run 1–2 per month."*

**Q4. What formula captures that value moment at the right frequency?**
> Write it as: `[count of users who did X] in [time window]` or `[rate of X per active user]`.
> *Example: "Monthly Active Skill Runs (MASR) = distinct users × avg skill completions per user per month."*

### NSM Validation Scorecard

After defining the NSM candidate, score it on each dimension (1–3):

| Dimension | 1 — Weak | 2 — Acceptable | 3 — Strong |
|-----------|----------|----------------|------------|
| **Value alignment** | Measures activity, not outcome | Loosely proxies user value | Fires exactly at the value moment |
| **Business correlation** | No link to revenue or retention | Weak correlation | Strong causal or demonstrated link |
| **Team alignment** | Only one squad can move it | Most squads contribute | Every squad has a clear input |
| **Frequency** | Quarterly or rarer | Monthly | Weekly or more |
| **Actionability** | A 20% rise changes nothing | Changes some decisions | Changes roadmap, resourcing, or OKRs |

**Scoring:** ≥12 points → accept the NSM. 9–11 → revise before accepting. <9 → reject and restart.

### Example (Vespyr)

```markdown
## North Star Metric: Vespyr CLI

**NSM Name:** Monthly Active Skill Runs (MASR)
**Formula:** COUNT(DISTINCT user_id WHERE skill_complete event in calendar month)
            × AVG(skill_complete events per user per month)
**Time window:** Monthly (with weekly leading indicator tracking)
**Data source:** Telemetry event `skill.complete` in artifacts/telemetry/

### Value Moment
The value moment fires when a user invokes a skill and an output artifact is
written to disk. This is the exact moment Vespyr delivered on its promise:
"your agent swarm did something you could not do alone in that time."

### Why this NSM, not alternatives
| Alternative considered | Reason rejected |
|------------------------|----------------|
| Total installs | Acquisition trap — installs ≠ value delivered |
| GitHub stars | Vanity — passive, no product usage signal |
| Total skill runs (absolute) | No per-user denominator; rises trivially with growth |
| DAU | Frequency trap — opening the CLI ≠ completing a skill |

### NSM Validation Score
| Dimension | Score (1–3) | Rationale |
|-----------|------------|----------|
| Value alignment | 3 | Fires exactly at skill completion = value delivery |
| Business correlation | 2 | Strong proxy for retention; revenue model TBD |
| Team alignment | 3 | Every squad (design, dev, devops, PM) has a clear lever |
| Frequency | 2 | Monthly cadence; weekly cohorts for leading signal |
| Actionability | 3 | A drop triggers immediate roadmap triage |
| **Total** | **13/15** | ✅ Accepted |

### Relationship to business outcome
When MASR rises, users are completing more workflows, which signals they are
retaining the tool and deriving ongoing value. High MASR users are the segment
most likely to recommend Vespyr, contribute skills back, and represent the
addressable base for any future premium tier.
```

## 1. Google GSM — Goals, Signals, Metrics

GSM is Google's internal framework for turning high-level product goals into precise, measurable metrics. It prevents metric sprawl by anchoring every number to a stated goal and an observable signal.

### Structure

```
Goal → Signal → Metric
```

| Layer      | Definition                                                                                                      | Question to ask                                       |
|------------|-----------------------------------------------------------------------------------------------------------------|-------------------------------------------------------|
| **Goal**   | A qualitative statement of what you want to achieve. Aspirational, but not yet measurable.                      | "What does success look like for this product area?"  |
| **Signal** | An observable behavior or change that would indicate the goal is being met. No numbers yet.                     | "How would we know, in principle, if this goal is being met?" |
| **Metric** | A specific, quantifiable measurement of the signal. Must have a formula, a baseline, and a target.             | "What can we actually count or calculate to confirm the signal?" |

### Three Metric Quality Tests (per GSM)

Before adding any metric to a plan, apply these tests:

1. **Sensitivity**: Will this metric actually move if the product changes in the intended direction?
2. **Specificity**: Does this metric only move when the product achieves the stated goal, not for other unrelated reasons?
3. **Explainability**: Can you explain to a non-technical stakeholder exactly what this number means and why it matters?

Metrics failing any test must be revised or dropped.

### GSM Template

```markdown
## GSM Metric Block: [Feature or Product Area Name]

### Goal
[One-sentence qualitative statement of what success looks like]

### Signal
[Observable behavior that would indicate the goal is being met — no numbers]

### Metric
- **Name:** [Short, descriptive name]
- **Formula:** [Numerator / Denominator × 100, or sum, or average — be precise]
- **Baseline:** [Current value, or "unknown — establish in first sprint"]
- **Target:** [Specific target by a specific date]
- **Measurement cadence:** [Daily / Weekly / Monthly]
- **Data source:** [Event log, analytics dashboard, database query]
- **Owner:** [@role responsible for tracking this metric]

### Sensitivity check
[How would this metric move if we shipped the feature? Would it move for the wrong reasons?]

### Anti-vanity check
[Why is this metric not a vanity metric? What decision would change based on this number?]
```

### Example

```markdown
## GSM Metric Block: User Onboarding

### Goal
New users should understand Vespyr's core value within their first session.

### Signal
A user completes at least one full skill workflow (e.g., /validate-idea through to an output file) in their first week.

### Metric
- **Name:** First-Week Skill Completion Rate
- **Formula:** (Users who complete ≥1 skill workflow in week 1) / (Users who installed Vespyr in week 1) × 100
- **Baseline:** Unknown — establish in Sprint 1
- **Target:** ≥40% by end of Q3 2026
- **Measurement cadence:** Weekly cohort tracking
- **Data source:** Telemetry event `skill.complete` joined with install date
- **Owner:** @data-analyst

### Sensitivity check
If onboarding UX improves, more users should complete a workflow in week 1. This metric would rise.
If we simply add more install channels, completions may stay flat or fall — that is a meaningful signal too.

### Anti-vanity check
Total installs would be the vanity metric. This metric forces us to ask: "Did those installs actually activate?"
A decision changes based on this number: if <25%, we cut the roadmap and fix onboarding.
```

## 2. Drivers Tree

A Drivers Tree (also called a Metric Tree or KPI Tree) is a causal decomposition that traces a top-level North Star metric down to the granular input levers that engineering and product can directly control.

### Purpose

- Prevents "one metric to rule them all" blindness — shows how the North Star is built.
- Gives each squad a specific input metric they own.
- Enables root cause analysis: if the North Star drops, trace it down the tree to find the broken branch.

### Tree Structure

```
North Star Metric
├── L1 Driver A (multiplicative or additive component)
│   ├── L2 Input A1 (directly actionable)
│   └── L2 Input A2 (directly actionable)
└── L1 Driver B
    ├── L2 Input B1
    └── L2 Input B2
```

Each node must satisfy:
- **Causal relationship**: A change in the child node mathematically or causally drives a change in the parent.
- **Owned by someone**: Each leaf node is assigned to a specific squad or role.
- **Measurable now**: The leaf metric must be traceable from existing or planned data.

### Drivers Tree Template

```markdown
## Drivers Tree: [Product or Feature Name]

**North Star Metric:** [Name] = [Formula]
**Rationale:** [Why this is the single best measure of product value]

---

### L1 Decomposition

**[North Star]** = **[Driver A]** × **[Driver B]**

*(or: [North Star] = [Driver A] + [Driver B] — choose whichever equation is mathematically accurate)*

---

### Full Tree

```
[North Star Metric]
├── [L1 Driver A: name and formula]
│   ├── [L2 Input A1: formula, owner: @role]
│   └── [L2 Input A2: formula, owner: @role]
└── [L1 Driver B: name and formula]
    ├── [L2 Input B1: formula, owner: @role]
    └── [L2 Input B2: formula, owner: @role]
```

---

### Lever Analysis

For each L2 leaf, document:

| L2 Input | Current Value | Target | Improvement Lever | Owner |
|----------|--------------|--------|-------------------|-------|
| [A1]     | [value]      | [target] | [what product/eng action moves this] | [@role] |
| [A2]     | ...          | ...    | ...               | ...   |
```

### Example (Vespyr)

```markdown
## Drivers Tree: Vespyr CLI Adoption

**North Star Metric:** Monthly Active Skill Runs (MASR)
= Count of distinct users × Average skill runs per user per month

**Rationale:** MASR captures both breadth (are people installing?) and depth (are people actually using skills regularly?), which is the core product promise.

---

### L1 Decomposition

**MASR** = **Monthly Active Users (MAU)** × **Average Skill Runs / Active User**

---

### Full Tree

MASR
├── Monthly Active Users (MAU)
│   ├── New Installs (weekly cohort, owner: @devops-engineer)
│   └── 30-day Retention Rate (%, owner: @product-manager)
└── Avg Skill Runs / Active User
    ├── Skills Discovered per Session (owner: @product-designer)
    └── Skill Re-run Rate (%, owner: @developer)

---

### Lever Analysis

| L2 Input | Current | Target | Lever | Owner |
|----------|---------|--------|-------|-------|
| New Installs | unknown | 500/month | Improve README, skills.sh discoverability | @devops-engineer |
| 30-day Retention | unknown | ≥35% | Fix onboarding, add first-session WOW moment | @product-manager |
| Skills Discovered/Session | unknown | ≥2 | Improve `help-me` skill surfacing | @product-designer |
| Skill Re-run Rate | unknown | ≥60% | Fix friction in skill invocation, reduce prompt steps | @developer |
```

## 3. Anti-Vanity Metrics Audit

Apply this checklist to every metric before committing it to a PRD, user story, or OKR. If any item fails, the metric is a vanity metric and must be replaced or redesigned.

### The Checklist

For each proposed metric, verify:

**A. The Decision Test**
> If this metric goes up by 20%, would the team make a different product decision?
- ✅ Yes → not a vanity metric
- ❌ No → vanity; replace with a metric that would change a decision

**B. The Denominator Test**
> Does this metric have a meaningful denominator (a rate, ratio, or per-user number)?
- ✅ Yes (e.g., retention *rate*, activation *percentage*, revenue *per user*) → likely actionable
- ❌ No (e.g., total downloads, total page views, raw registrations) → likely vanity

**C. The Isolation Test**
> Can you change this metric through product improvements alone, or does it also rise with external noise (e.g., viral moment, press coverage, ad spend)?
- ✅ Mostly product-controlled → actionable
- ❌ Heavily confounded by externals → supplement with cohort/segmented analysis or replace

**D. The Segment Test**
> Can you disaggregate this metric by user segment, feature, or time cohort to make it actionable?
- ✅ Yes → metric has diagnostic depth
- ❌ No (a single undifferentiated number) → add a dimension or replace

**E. The Guardrail Test**
> Does optimizing this metric risk harming another important metric (e.g., engagement gaming that hurts retention)?
- ✅ A guardrail metric is in place to detect this trade-off → safe to use
- ❌ No guardrail defined → add one before locking this metric in

### Common Vanity Metrics to Avoid (with Replacements)

| Vanity Metric | Problem | Replace With |
|---------------|---------|--------------|
| Total downloads / installs | Doesn't measure value delivery | First-week skill completion rate |
| Total registered users | Many never return | Day-7 / Day-30 retention rate |
| Total page views | Volume without engagement signal | Session depth (pages/session), scroll depth |
| Total social follows | Passive attention, not product usage | Monthly active engagement rate |
| Total revenue (raw) | Hides churn and quality | Net Revenue Retention (NRR), ARR |
| App store rating (raw average) | Gameable; survivor bias | % 5-star reviews from activated users |
| Feature usage count (absolute) | Grows with installs, not per-user value | Feature adoption rate (users who used feature / MAU) |

## 4. Applying the Frameworks Together

Use all four tools in this sequence during metric definition:

```
Step 0: Define the North Star Metric (NSM)
        → Answer the Four Questions; validate with the Scorecard (≥12/15)
              ↓
Step 1: Build the Drivers Tree
        → Decompose the NSM into L1 and L2 causal leaf metrics
        → Assign an owner (@role) to every leaf node
              ↓
Step 2: Apply GSM to each node
        → Anchor every metric to a Goal + Signal before writing the formula
        → Apply Sensitivity, Specificity, and Explainability tests
              ↓
Step 3: Run the Anti-Vanity Audit
        → Apply all five tests (Decision, Denominator, Isolation, Segment, Guardrail)
        → Reject or redesign any metric that fails
              ↓
Step 4: Finalize and record in the PRD (Section 6: Success Metrics)
        → Assign owners, baselines, targets, and measurement cadence
        → Confirm data source availability with @data-analyst
```

No metric enters the PRD if it has not passed through Steps 0–3. Coordinate with `@data-analyst` to confirm data availability for all leaf-level metrics before finalizing.
